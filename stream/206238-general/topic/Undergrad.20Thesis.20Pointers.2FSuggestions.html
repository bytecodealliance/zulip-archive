You mentioned optimization so one thing that might make a very interesting, and also tractable, undergrad thesis is some sort of systematic study of the "optimization gap" between Cranelift and, say, LLVM or V8 or SpiderMonkey. For any given input (say Wasm via some LLVM-based Wasm engine, V8, and Wasmtime+Cranelift), look at the machine code that comes out from each and try to categorize/root-cause reasons for any perf gap. It's a more analysis-heavy thesis topic but one could then try to implement anything missing, or maybe fake it (do it by hand) for certain benchmarks, to categorically understand the tradeoffs. We've wanted a deeper understanding of "what's left to do" for a while and so this would actually help us a bunch too.

Will say more if I think of any other ideas! Best of luck...

fitzgen (he/him) (Oct 01 2026 at 17:19):

@Hari Mohan a couple more ideas:

  • finish https://github.com/bytecodealliance/wasmtime/issues/5783 -- we have infra scripts for harvesting souper superoptimization candidates from wasm files and then run souper on those candidates to generate missing optimizations, and we even have some generalized optimizations that we need to write in ISLE as new mid-end rules. but we haven't taken the time to do that yet. and this is something that can be done repeatedly in a loop and for a variety of different benchmarks/wasm programs and such.
  • regalloc2 has a register allocation checker that proves various correctness properties for a given register allocation. our safepoint spiller code in cranelift-frontend is basically a register allocator if you squint, and we have historically had a bunch of bugs due to missing stack maps due to things like bugs in the liveness analysis that the safepoint spiller uses. it would be really awesome to implement a "safepoint" checker that is similar to regalloc2's register allocation checker but specifically for safepoints and stack maps

happy to go into more details if you anything interests you...

Chris Fallin (Oct 04 2026 at 23:23):

@Hari Mohan a few thoughts on the "perf analysis and followups" track:

  • I don't necessarily think that the outcome will be "a suitably general rewrite rule ... in ISLE". Many of the optimizations we might need to do in the future are not simple value-to-value substitutions -- e.g. better alias analysis, or escape analysis, or loop vectorization, or a deficit in regalloc, or better inlining heuristics, or something like that. My point isn't that any of those specifically might be useful but rather that the scope is "the entire compiler" and ISLE rewrite rules make up only two specific phases (mid-end rewrites and back-end instruction selection).
  • So I'd see the outcome as rather "I compared these benchmarks and found that the same code, [compiled natively via LLVM / compiled via V8 as a Wasm / ...], was significantly faster because [50% due to regalloc shortcomings, 37% due to weak alias analysis, ...]". That then directs effort in the second half.
  • Since "simply building an LLVM-equivalent compiler" is definitely not within the scope of an undergrad thesis project (or any individual person's project! it's engineer-decades potentially!), the "second half" might be something like: you manually transformed the benchmark kernels with the transform you wish Cranelift had done, and doing the transform step-by-step, you show performance come up step-by-step to baseline (LLVM, V8, ...) levels.
  • So it's really an "understanding the gap" project, not a "filling the gap" project.
  • I forgot to mention above but the biggest gaps you are likely to see will be not in Wasms on Wasmtime+Cranelift vs V8 or vs SpiderMonkey or LLVM-Wasm-frontend-of-choice + LLVM, but on other code compiled via Cranelift vs other compilers. The reason is that most Wasms are themselves produced by optimizing toolchains, so there is actually not too much low-hanging fruit remaining (in our recent experience at least). But if you take, say, the Rust frontend and its LLVM vs Cranelift backends, you might find a lot more of a gap, and more interesting optimization opportunities.

Chris Fallin (Oct 07 2026 at 23:15):

  • Re: benchmarks: we have a pretty good collection of programs in Sightglass and you could try (for those in Rust, or for Rust translations) compiling them directly with either cg_clif or Rust-LLVM. I'd encourage diversity of benchmarks -- my experience (with regalloc and the mid-end optimizer at least) is that it's easy to overfit if you only have a few.
  • Yes, I think coming up with ways to compare is one of the big methodological questions here (in other words, a place where you can be inventive). One thing you might try is to find correlations -- e.g. by function name -- and then try to match up equivalent code, by hand at first, maybe with some automation later. In my experience the set of hot blocks / hot loops in any given benchmark is fairly small (i.e. there is often a kind of power-law going on in code hotness distribution) so there is relatively little code to compare in many cases. Not all benchmarks are like this (famously in SPECint, gcc-as-a-benchmark has a big code footprint that is very "flat")
