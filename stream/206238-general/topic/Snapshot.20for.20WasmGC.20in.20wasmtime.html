Topic: Snapshot for WasmGC in wasmtime

Dmitry Bezhetskov (Nov 06 2026 at 14:28):

Hey! Since quite a few new language runtimes are targeting WasmGC, I think it would be great to have something similar to Wizer, but with support for GC types.

This would require support from the host runtime, so I think Wasmtime would be a perfect fit.
I imagine the design could follow V8's snapshot mechanism: serializing the GC heap while allowing embedders to provide custom callbacks for serializing and deserializing host-managed state.

Does anything like this already exist in Wasmtime?
If not, would you be interested in adding it?

Till Schneidereit (Nov 06 2026 at 19:14):

it doesn't yet exist, but we've talked about it. Wasmtime's implementation of WasmGC would lend itself very well to it, too, since the GC heap is itself a linear memory. On whether we'd be interested in adding it: in principle yes! In practice, I think it depends a bit on how much review and then ongoing maintenance effort it'd be, and what the security implications would be. @fitzgen (he/him) would be able to say more

fitzgen (he/him) (Nov 06 2026 at 20:55):

it is possible, but the other thing to keep track of is the collector's outside-the-heap state. this could potentially be marked #[derive(Clone, serde::Serialize, serde::Deserialize)] and plumbed through the GcHeap trait methods but it might not be exactly what we'd actually want to do. But the snapshots would be tied to a specific version of Wasmtime, and could break even across patch versions. and ofc they would not be engine independent anymore, like Wizer snapshots. with enough special reflection APIs in the engine you could encode the snapshot as core Wasm and just have code to rebuild the heap graph on demand, which gives the portability back, but costs initialization performance.

I was actually just talking with @Chris Fallin about this kind of thing yesterday, but in the context of record/replay and time travel debugging, where there are slightly different constraints (perf is important but perhaps not quite to the same degree, portability across engines is highly desirable for the recording but a snapshot never actually needs to persist across a single process, etc...)

But backing up, while I don't think anything here is impossible with enough effort, I don't believe this is something that we have bandwidth to review+maintain from a contributor who is not a core maintainer.

Chris Fallin (Nov 06 2026 at 21:04):

It seems likely to me that "snapshot back to initialization expressions / a synthesized init function that ties the knot on any cycles" is the better answer to produce a portable Wasm that contains the GC snapshot. That then composes with our wasm -> cwasm AOT compilation step to potentially give a GC heap snapshot (tied to a specific Wasmtime version because the whole cwasm is) that can provide a CoW backing for fast instantiation. In other words, Wasm spec-level description goes with Wasm, byte-level description goes with cwasm-for-this-Wasmtime-version.

(I recall early discussion here on Zulip somewhere about exactly the above re: const-expression GC ops + code to tie the knot; can't find it at the moment)
