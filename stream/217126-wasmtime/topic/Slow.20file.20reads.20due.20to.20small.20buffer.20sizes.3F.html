Topic: Slow file reads due to small buffer sizes?

Justin Fagnani (Oct 13 2026 at 17:12):

I'm working on streaming file contents read from wasi:fs and passed out to wasi:http and I noticed that the throughput was pretty slow even though by forwarding the WASI stream, my guest code shouldn't be in the byte-serving path. I was getting about 261 MB/s on my server vs 3.4 GB/s for Python serving a random 64 MB file.

It seems like the issue might be the 8k DEFAULT_BUFFER_CAPACITY. I had an agent run a benchmark against different values, and got these results:

read size 64 MB
8 KiB (stock) 245 ms
64 KiB 31 ms
128 KiB 23 ms
256 KiB 16 ms
512 KiB 13 ms
1 MiB 11.5 ms

There's not currently a way for an embedder to directly change the buffer size, but you can accomplish that by overriding read-via-stream (as an agent did for me here: https://github.com/elematic/zena/pull/324).

Would it be worth a way to allow an embedder to easily change this, and/or increasing the default value?

I'd also be interesting in a way to set buffer sizes from guest code, but that would be a WASI question.

Roman Volosatovs (Oct 16 2026 at 17:13):

Making DEFAULT_BUFFER_CAPACITY configurable by embedders definitely makes sense to me, and I think it would be the lowest-hanging fruit providing the biggest immediate benefit.

If I understand this correctly, we're in the host<->host case, where the wasi:filesystem producer is streamed to a wasi:http consumer. If the other side were the guest, the host would know the guest's buffer capacity and could do what's optimal, however in this case the buffer is preallocated using DEFAULT_BUFFER_CAPACITY, so ultimately I think we want the consumer to be able to say how many elements it needs, rather than having the producer use an arbitrary value. In some sense I think we want this to behave more like https://docs.rs/tokio/latest/tokio/io/trait.AsyncRead.html

In other words, we'd need https://github.com/bytecodealliance/wasmtime/blob/3c4c9651687c4c9abd1ad6333a1b0416c0ac76fc/crates/wasmtime/src/runtime/component/concurrent/futures_and_streams.rs#L399-L417 to return a value for host consumers as well, although I'm not sure we'd want to structure the API that way

Long term, I think we want to make DEFAULT_BUFFER_CAPACITY redundant altogether in this case (although we'd still want a configurable cap)

IIRC we actually discussed this a while back with @Joel Dice
