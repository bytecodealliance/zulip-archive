fitzgen (he/him) (Nov 10 2026 at 15:53):

Alex Crichton said:

how come the results are rolled up and made for a series of commits? Does AWFY run on a fixed schedule and just benchmark whatever's there? If so, would it be possible to refactor to run for individual commits or is that expected to take too long?

It runs on a cron job scheduled every 2 hours, but each benchmarking run takes up to ~2.5 hours and we limit concurrency to 1. So it just benchmarks whatever new commits are there since the last job (or doesn't benchmark anything if there are no new commits)

We could look into lifting the concurrency limit (since running the cron more frequently won't change much given that a run takes longer than the scheduled interval) but then we also have to figure out how to merge automatically results better, since a previous run won't have finished and been committed before we kick off the next run. And the data for runs is stored in incrementing ID directories...

Also not sure we want to burn more of our CI time on this or not.

What I've been doing when there is a regression range is try to bisect locally to figure out which exact commit(s) are responsible. I guess we could also look into automating the bisect?

It seems like (with the baseline assumption that building infra is easier now than it would have been otherwise) a bisect that only runs the benchmarks that showed statistical movement in the rollup run would be both useful, and much faster/cheaper. That does have the potential to miss a benchmark that moved one way in commit N then exactly canceled out in N+1 in the rollup, but for most common cases of "two different orthogonal signals are contained here" it seems cheap and easy (in terms of CI time)?
