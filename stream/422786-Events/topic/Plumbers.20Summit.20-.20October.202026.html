Lucy Menon (Oct 28 2026 at 16:36):

@Chris Fallin I really liked the watchpoint CoW scheme. I'm kind of curious how that works/whether there are scalability limits on it, since one usually has a pretty limited number of watchpoint ranges available?

Also: a bit out of scope for this talk, but looking to the future since you mentioned heisendebugging earlier: do you have any thoughts on whether/how you might be able to in the future explore thread schedules/weak memory interleavings when multiple parallel threads (e.g. via shared-everything thread.new) arrive?

Chris Fallin (Oct 28 2026 at 16:39):

@Lucy Menon great questions!

  • watchpoints: the high-level idea is that we have a shadow memory that is 1-to-1 with the memory it's attached to. On a store, we first load the same width/offset and check if nonzero in the shadow, and libcall for debug event if so. (So, "software watchpoints"). So fully scalable, at the cost of a constant tax on every store instruction.
  • Thread schedules and memory interleavings in shared-memory threads: interesting! I have some vague handwavy thoughts about enforcing determinism with "write protection" via the above watch points, similar to how we capture dirty pages; basically a software cache coherence algorithm. I guess in principle we then have a choice-point when we have multiple waiters for a page and we could instrument to tweak that for testing/exploration if we wanted to...
