Topic: Trouble virtualizing wasi interfaces

Scott Andrews (Oct 20 2026 at 18:10):

I'm working on a suite of components that virtualize WASI interfaces (wrapping each interface to trace calls, apply access controls, etc.). I've hit a limitation in the 0.3 async model that I don't think wrappers can work around.

The concrete case is wasi:http/types request.new, a sync function that accepts trailers: future<result<option<trailers>, error-code>>. The virtualizer's exported trailers is a distinct resource type from the imported one, so that future can't be forwarded to the upstream request.new. Something has to await it, unwrap the resource, and write a new future. But a sync-lifted export has no task that outlives the call. Once it returns, the component can't run until it's called again. Blocking inside new would deadlock, because the caller only writes trailers after new returns.

wit-bindgen 0.62 papered over this: spawn_local from a sync export queued the work, and it ran during whatever async export came next. 0.63 now reasonably asserts there's an active task, which surfaced the problem: https://github.com/bytecodealliance/wit-bindgen/issues/1754. Even before that, my approach was inherently fragile.

The pattern isn't specific to http. Any sync function that takes or returns a future/stream whose payload contains a resource has this problem (request/response.new, consume-body, and I believe wasi:sockets tcp-socket.listen). Streams of plain data can be passed through, but can't be observed without a task either (e.g. wasi:cli write-via-stream).

Colorless composition was an early goal that has narrowed. It leaves sync functions with no way to start work that continues after they return. Some directions I can see, none of which I'm confident in:

  1. Allow sync-typed functions to be lifted with the async ABI, keep running after task.return, and trap only if they block before returning.

  2. Let cooperative threads outlive the sync task that created them.

  3. Require any WIT function that takes or returns a future/stream to be async. This works, but it pushes the cost onto every caller.

Is there an intended pattern for this, or is the ability to virtualize any interface not a goal the current design can guarantee? I know just enough here to be dangerous, and deeply appreciate the effort put into the design to date.

Till Schneidereit (Oct 23 2026 at 10:24):

an aside: I find it odd that a platform with a zero capability by default model would default to enabling every capability on the host for the premier build target.

You're not wrong that it'd be a lot nicer conceptually if we could avoid this. The reality is, though, that we need to meet developers where they are for any of this to be useful. And developers exist in established ecosystems, backed by language standard libraries and package repositories that fundamentally expect these interfaces to exist.

(An aside to my answer to your aside: making interfaces available isn't the same as making capabilities available. E.g., wasi:filesystem being available doesn't mean you have access to any particular file handle, or the ability to gain that access. The actual capabilities system isn't ideal, but also far stronger than "default[ing] to enabling every capability on the host".)

Scott Andrews (Oct 23 2026 at 11:27):

My concern is less that their is a way to turn these imports on, and more that their isn’t an obvious way to turn the off. I agree that existing language ecosystems expect these capabilities, because that’s how it’s always been. Components disrupt that status quo.

Of course the host, or another component can limit the capabilities. I’m working on exactly that. It’s a powerful ability with components that two different branches of a composition can have different degrees of access to a capability like wasi:sockets.

That doesn’t preclude my stance that a component which doesn’t need the network, should never have access to the network. Latent capabilities that aren’t used today, have a history of becoming tomorrow’s security vulnerabilities.
