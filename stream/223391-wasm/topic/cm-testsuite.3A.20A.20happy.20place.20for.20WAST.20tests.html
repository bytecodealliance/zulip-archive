After some discussion a few weeks back that included an @Alex Crichton wish-casting session, I've gotten to working on cm-testsuite, an attempt to build an authoritative source (and sink) for WAST tests that validate Component Model behavior.

📋 Component Model Test Suite

Context

While wasi-testsuite exist and is load bearing in some contexts, it's meant for WASI tests, and WASI releases/versions may include certain CM features but are not tied to them.

Right now we have many ways of testing component model features -- mostly WAST tests and component tests built from source code, and of course in-source-code tests, and even Python tests . The second implementation (Jco) is currently also a sort of a "test" in some respects of the ability to interpret and implement the CM.

When it comes to testing implementations, WAST while a custom format (note it's note quite the same as WAT -- it supports stanzas that are not normally present, which downstream users must implement) is the best cross-language method (a "wedge", even, some might say) we have... So what we need is a big repository of known-good WAST tests.

What cm-testsuite adds

cm-testsuite looks to add one thing in particular: a central repository for WAST tests.

Note that it is up to engines/CM implementations/etc to use/run the tests themselves, and manage their own set of private tests if they'd like (of any variety).

Outside of the core goal of catching all the WAST tests, cm-testsuite introduces a lot of machinery to make maintaining, "gathering" and "distributing" WAST very easy to do, mainly via CI automation and GH pull requests. That machinery is somewhat beside the point, and there should not be much surprise there

Easier ways to consume WAST tests

The point has been brought up that integration of these tests even while automated heavily is still too heavy for some projects.

With this point in mind, we're leaning towards adding new ways of consuming the tests (and I'm open to suggestions):

  • A "Latest" release that updates on every push to main and contains a .tar.gz with every current test
  • A (submodule-able) git branch that is updated on every push to main and contains a folder with every current WAST test
  • S3???

These mechanisms are meant for teams that basically have their own machinery in place, and want something to slot in with the smallest amount of integration (i.e. no extra TOML or configuration of receiving/sending tests, no public repos, etc).
