Closes #14752

GuestProfiler::new rebuilds and re-demangles each module's symbol table on every call, which costs milliseconds for large modules.

With this change, now the use of the profiler can be, optionally, split into a prepare step (where you make a GuestProfilerModules struct which is an expensive but now one-time operation) separate from the profiling step - where you pass that GuestProfilerModules into the profiler.

The standard GuestProfiler::new just does that internally, so existing callers don't have to change. But - and wasmtime serve does this now - you have the option of disentangling and caching the expensive demangling effort.

Added refs to this in the profiling documentation.

As it seemed practical to mirror this in the C bindings I went ahead and did that as well. I'd be happy to leave wasmtime serve alone if you prefer, but I felt that it would be good to see example code.

Changes

  • GuestProfilerModules: a new public type for the modules a profiler attributes samples to. It is prepared once and cheap to clone, since the prepared modules sit behind an Arc.
    • GuestProfilerModules::new and new_component do the per-module work that GuestProfiler::new used to repeat for every profile: the guest-debugging check, each module's text range, and its demangled symbol table.
    • The table-building code moves unchanged into module_symbol_table.
  • GuestProfiler::new_with_modules(module_name, interval, &modules): starts a profile from a prepared set. It needs no Engine and can't fail, because the checks already ran during preparation.
    • It adds each library without its table, then attaches the shared table with Profile::set_lib_symbol_table.
    • Profile::add_lib keys libraries by value, so a table carried inside LibraryInfo would be hashed, every name included, on each new profile.
  • GuestProfiler::new and new_component: keep their signatures. They now build a set and call new_with_modules. Module is unchanged.
  • wasmtime serve --profile=guest: starts a profiler for every instance. It now prepares the component's modules once, when the server starts, and uses new_with_modules for each instance.
  • C API: adds wasmtime_guestprofiler_module_set_t with wasmtime_guestprofiler_module_set_{new,clone,delete} and wasmtime_guestprofiler_new_with_module_set. The array conversion shared with wasmtime_guestprofiler_new now accepts a NULL pointer with zero length.
  • Docs: rustdoc for the new items, including an example that runs as a doctest, plus a short embedding note in the guest profiling page of the book.

Measurements

Release build, x86_64 Linux, median of 1000 calls, using the issue's reproduction program extended to call the new API. The 1.7 MB module is a real Rust module with about 1,500 functions.

Module Before: new() After: GuestProfilerModules::new (once) After: new_with_modules (per profile)
1,500 functions 663 µs 679 µs 0.95 µs
10,000 functions 4.52 ms 4.63 ms 0.95 µs
Real 1.7 MB module 2.39 ms 2.37 ms 0.95 µs

The per-profile cost no longer depends on how many functions a module has. The previous revision still spent about 8 ns per function on each profile. That was the walk over every function to find the module's text range, which now runs once during preparation.
