Followup from https://github.com/bytecodealliance/wasmtime/pull/15115:

Going full no_std with cargo b -p cranelift-codegen --no-default-features --features all-arch still fails to compile due to s390x using f32::powi(), which is a #[rustc_allow_incoherent_impl] so even though it's declared in core, it only "exists" in std. [...]

Note that libm doesn't have a dedicated f32::powi() implementation, so crates like num-traits implements it by wrapping powf.

There's a couple options to implement this:

  1. What this PR does: Fallback to libm::pow if std feature is disabled. I decided against adding the num-traits crate and just add my own cfg switch.
  2. Always use libm to guarantee bit exact results across different platforms. This may change s390x artifacts as the new function may be off by some other amount of ulps than the compiling machine's fp unit.

Which one do you prefer?

This is only used to compute (relatively) small powers of two, specifically 2^31, 2^32, 2^63, and 2^64. Those should always provide exact results. I would hope that just using pow/powf would also be fine here, since those results should also be exact.

In the alternative, I guess we could also compute the power-of-two as an integer and only convert the result to float. That might be an issue with 2^64, but there we can compute 2^63, convert to float, and double the float.

I don't think providing two different code paths is helpful here.
