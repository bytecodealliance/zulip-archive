.clif Test Case

A function with N loops in a row. Each loop adds its counter to a sum until the counter reaches the second argument,
then stores the sum and starts the next loop. It is written as an optimize filetest, so that clif-util test runs
the egraph pass alone. Here N = 2:

test optimize
set opt_level=speed
target aarch64

function %loops(i64, i64) {
block0(v0: i64, v1: i64):
    v2 = iconst.i64 0
    v3 = iconst.i64 1
    jump block1(v2, v2)

block1(v4: i64, v5: i64):
    v6 = iadd v5, v4
    v7 = iadd v4, v3
    v8 = icmp ult v7, v1
    brif v8, block1(v7, v6), block2

block2:
    store v6, v0+8
    jump block3(v2, v2)

block3(v9: i64, v10: i64):
    v11 = iadd v10, v9
    v12 = iadd v9, v3
    v13 = icmp ult v12, v1
    brif v13, block3(v12, v11), block4

block4:
    store v11, v0+16
    jump block5(v2, v2)

block5(v14: i64, v15: i64):
    return
}

gen.sh writes the same test at any N:

#!/bin/sh
# Writes a test of the egraph pass on N loops in a row, each summing its counter until the counter reaches n and
# storing the sum at p + 8 * i.
n=${1:-4}
printf 'test optimize\nset opt_level=speed\ntarget aarch64\n\nfunction %%loops(i64, i64) {\nblock0(v0: i64, v1: i64):\n    v2 = iconst.i64 0\n    v3 = iconst.i64 1\n    jump block1(v2, v2)\n'
i=1
while [ $i -le $n ]; do
  v=$((5 * i - 1))
  printf '\nblock%d(v%d: i64, v%d: i64):\n    v%d = iadd v%d, v%d\n    v%d = iadd v%d, v3\n    v%d = icmp ult v%d, v1\n    brif v%d, block%d(v%d, v%d), block%d\n\nblock%d:\n    store v%d, v0+%d\n    jump block%d(v2, v2)\n' \
    $((2 * i - 1)) $v $((v + 1)) $((v + 2)) $((v + 1)) $v $((v + 3)) $v $((v + 4)) $((v + 3)) $((v + 4)) $((2 * i - 1)) $((v + 3)) $((v + 2)) $((2 * i)) $((2 * i)) $((v + 2)) $((8 * i)) $((2 * i + 1))
  i=$((i + 1))
done
printf '\nblock%d(v%d: i64, v%d: i64):\n    return\n}\n' $((2 * n + 1)) $((5 * n + 4)) $((5 * n + 5))

Actual Results

Compile time grows quadratically with N: at N = 16,384 the egraph pass takes 0.30 s, and with the patch 0.046 s. The
instructions retired by clif-util grow 2.2, 2.6 and 2.9 times per doubling of N, and those beyond the patched run's
grow 4.0 times, while peak memory does not quite double:

N Egraph pass Instructions retired Peak memory
2,048 0.013 s 0.56G 16 MB
4,096 0.025 s 1.21G 24 MB
8,192 0.086 s 3.11G 41 MB
16,384 0.302 s 9.08G 69 MB

The pass times are the first column of -T. The instructions retired include parsing and verification. Each figure is
from one run, on a machine whose load average was about 47 at the time.

Extra Info

When elaboration places a pure instruction, it looks for the outermost loop that the instruction can be hoisted out
of. For each argument, it scans loop_stack[..active_loop_depth] from the outside in, for the first loop whose hoist
block is dominated by the block where the argument is available. An argument computed inside the current loop, such
as a counter or a sum, is not available at any hoist block, so the scan reads the whole slice.

The slice is not only the loops that contain the current block. A loop is popped from loop_stack when the walk of
the dominator tree leaves its header's subtree, and in the test case every block after a loop is in that subtree, so
every earlier loop in the row stays on the stack. find_active_loop_depth returns the position just past the
innermost loop on the stack that contains the block, so the slice includes every earlier sibling too. In the k-th loop
of the test case the slice has k entries, and the scan reads all of them for every argument computed in the loop.

A profile of stock clif-util test at N = 32,768 shows 516 of the egraph pass's 531 samples in this scan, a loop of
DominatorTree::block_dominates calls over the stack's entries.

The patch finds the same level by a binary search. Each loop header on the stack is dominated by the one before it,
so each hoist block strictly dominates the next. A value available at one hoist block is therefore available at
every later one, and the predicate of the scan is false for a prefix of the stack and true for the rest.
partition_point returns the first entry where it is true, and the length of the slice where it never is, as the
scan's unwrap_or(active_loop_depth) did.
