cfallin opened PR #15083 from cfallin:isle-veri-cache-s3 to bytecodealliance:main:

This PR addresses some problems we've had with the current "cached SMT query solver" implementation we have on top of GitHub CI's builtin cache action. In particular, the current cache action seems to refresh its cache once per night; so on a change that invalidates most of the cache (which may plausibly happen with any crosscutting change to the verifier itself or some base-level lowering rules or helpers), all CI jobs on that day will take multiple hours to run.

This PR instead implements a cache on top of an S3 bucket that we control separately. The basic data structure is a bit like an LSM tree: there is a packfile with sorted keys/values, and there are delta files that can be uploaded with new keys/values. Every so often, the current base packfile and deltas are consolidated into a new base packfile. This design is meant to minimize the number of PUT requests to S3 (which are relatively expensive) and the number of GET roundtrips (which can have nontrivial latency): ideally, we (i) have one or just a few big binary downloads to get the whole cache, and (ii) do no uploads if nothing changed, or one upload with everything that changed otherwise.

The read/write scoping is somewhat subtle too: previously we relied on GitHub CI's built-in key scoping hierarchy, with main CI runs implicitly visible to all PR branches, and each PR having its own private key-space. With this PR, we now have a simpler design: CI jobs on main will write the S3 cache (using a secret visible only to CI), and jobs on branches will read the cache. The cache bucket is publicly readable, so any job can query it without a secret. This keeps the AWS secret away from CI runs on branches, which we might not have fully vetted yet.

With this design, any change that merges to main will have its new cache entries immediately available to all PRs based on it, once it merges, so a cross-cutting change that invalidates a lot of the cache should only cause one long CI run in the merge queue.
