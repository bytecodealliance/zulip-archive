Fixes https://github.com/bytecodealliance/wasmtime/issues/14804

CacheConfig::validate bounds the two *-limit-percent-if-deleting settings to
0-100, but nothing bounds file-count-soft-limit and
files-total-size-soft-limit, which are plain u64 values. The cleanup task
computed the deletion threshold as
limit.checked_mul(percent as u64).unwrap() / 100, so a valid configuration
such as file-count-soft-limit = "18446744073709551615" with 70% panics with
called Option::unwrap() on a None value as soon as the first cleanup runs. The
panic is on the cache worker thread, so the CLI keeps running with a
permanently dead cache worker.

This computes the percentage without widening the type and without overflowing
any intermediate: value / 100 * percent + (value % 100) * percent / 100 is
exactly floor(value * percent / 100), and neither term exceeds value for
percent <= 100. Large soft limits stay usable as an "effectively unlimited"
setting, so no new bound is added to the validation.

Tests:

  • test_percent_of cross-checks the helper against u128 arithmetic for values
    around u64::MAX and percentages from 0 to 100, including the case that used
    to panic.

  • test_on_update_cleanup_max_soft_limits runs the cleanup task with u64::MAX
    soft limits and asserts that it neither panics nor deletes recognized cache
    entries (unrecognized files are still removed). It calls
    handle_on_cache_update directly, because a panic on the worker thread would
    otherwise hang the test harness.
