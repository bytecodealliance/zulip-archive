:memo: alexcrichton submitted PR review:

Do you have an immediate use case for this at the moment, and if so could it use wasm-tools compose or wac in the meantime?

I'm hesitant myself to start committing to something here becuase there's a lot that's possible in this space and I'm not sure that this is the best approach. Some thoughts I'd have are:

  • Technically --preload should be able to work for core wasm modules loaded into a component, that'd satisfy a component importing a core module for example.
  • Val is so horrendously slow that I'd rather not feature it so prominently within the implementation of an option that I suspect everyone expects to be fast.
  • Instead of using Val our thinking historically has been that something performs a composition and Wasmtime sees the composition, so for example wasmtime --preload could compose on-the-fly like it does with unsafe builtins or perhaps something similar to that.
  • Overall repurposing --preload as-is from core modules may not be the best design here. In theory this could support behavior like -L on linkers where the idea is you can point wasmtime to various directories to automatically find and load *.wasms as appropriate.

Basically I'm not confident that we should take --preload as-is and support it within the CLI, and I'm also not confident in the implementation using Val. That's what leads me to ask if a composition works for your use case if you have one. Otherwise though I think it's fine to work through these questions/ideas, but I'm not sure if that's what you were expecting to do here.
