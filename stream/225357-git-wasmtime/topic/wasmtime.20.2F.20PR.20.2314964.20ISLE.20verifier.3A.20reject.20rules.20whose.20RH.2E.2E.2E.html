Bug

#14957 reported an unsound ISLE rule passing the VeriISLE verifier. This is my take on why it passes currently and my attempt to fix it.

In the given example, cty is the result type of both sextends, but nothing bounds x and y to the same width. The verifier currently reports skipped type assignments (102 in the example) and verifies the 6 where x, y, and ty happen to have the same width. So a rule like

(ireduce ty (iadd cty (sextend cty x) (sextend cty y))) => (iadd ty x y)

was accepted even though x and y may differ in width.

This Fix

A rule fires whenever its left-hand side matches, so its right-hand side must be well-typed under every type assignment the left-hand side accepts. If it isn't, then the rule should be rejected.

This commit changes the verifier so that:

  • We mark which parts of the rule come from LHS or RHS.
  • Solve LHS types first, then check RHS under each satisfying assigment.
  • Report the RHS conflict as error.

Caveat

This addition type check step needs the solver, so --skip-solver would still skip these conflicts.

Bug

#14957 reported an unsound ISLE rule passing the VeriISLE verifier. This is my take on why it passes currently and my attempt to fix it.

In the given example, cty is the result type of both sextends, but nothing bounds x and y to the same width. The verifier currently reports skipped type assignments (102 in the example) and verifies the 6 where x, y, and ty happen to have the same width. So a rule like

(ireduce ty (iadd cty (sextend cty x) (sextend cty y))) => (iadd ty x y)

was accepted even though x and y may differ in width.

This Fix

A rule fires whenever its left-hand side matches, so its right-hand side must be well-typed under every type assignment the left-hand side accepts. If it isn't, then the rule should be rejected.

This PR changes the verifier so that:

  • We mark which parts of the rule come from LHS or RHS.
  • Solve LHS types first, then check RHS under each satisfying assigment.
  • Report the RHS conflict as error. But don't report assignments that can never occur due to a guard like (value_type ty).

What the new check found

Making these conflicts visible exposed rules that previously verified vacuously, because every type assignment was silently dropped. For example, the sdiv_base_base_64 rule uses (writable_zero_reg) as a 64-bit destination register. But its spec was a fixed 32-bit value:

(spec (writable_zero_reg) (provide (= result #x00000000)))

All the type assignments conflicted and were dropped. In this case the problem was the spec, but treating "no type assignment works" as "this rule doesn't apply" also hid this problem.

Mid end (opt)

The x > max(x, y) --> 0 rules in arithmetic.isle reuse one ty for a comparison's result type and for its operands. When matched, the type of an icmp is its result type (i8), so these rules only fire for i8 operands. The verifier also can't relate that ty to the comparison's width. I've tagged them TODO here. Switching them to a separate comparison type changes optimizer output, so it will be a separate PR.

aarch64 lowering

With the help of an LLM I made some fixes to the new lowering verification errors on aarch64.

  • writable_zero_reg was a fixed 32-bit zero but is used as a 64-bit destination. It is now polymorphic.
  • writable_reg_to_reg required equal widths, but scalar float helpers allocate 128-bit vector temporaries and return them as 64-bit Regs. It now keeps the low bits.
  • FixedToFP! narrowed its operand to the destination float width before converting, so fcvt_from_{u,s}int.f32 of an i64 only converted the low 32 bits. It now converts at full width, as the CLIF spec already does.
  • Load and store addresses are scalars, but their specs left the lane count open, so the verifier could pick a vector address. The specs now say it's a scalar.
  • trap_if_div_overflow emits flag-setting and flag-consuming instructions without threading the flags, which the specs don't model.

Enabling with_flags

Verifying sdiv overflow check needs with_flag, which was tagged TODO. Removing it brings flag-using lowering rules into scope, and some of them fail or have no spec. I've excluded the specific cases as TODO. I think this is OK because they were all excluded before, just implicitly.

Caveat

This addition type check step needs the solver, so --skip-solver would still skip these conflicts.
