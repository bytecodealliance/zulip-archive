In the last Cranelift meeting, we discussed the semantics of load merging and the various memory flags, such as can_move, readonly, and notrap, and which of these permits GVN'ing redundant loads together.

We concluded that for a load marked only readonly (so, may trap and cannot move), it should still be safe to GVN that load against earlier identical loads that dominate it. THe current egraph mid-end does not do this.

The GVN-of-side-effecting-but-idempotent ops is fundamentally gated by is_mergeable_for_egraph, and in that function, we previously excluded all loads and stores, with the rationale that (i) readonly + can-move + notrap loads are truly pure and will be handled by the ordinary egraph GVN mechanisms, and (ii) all lother loads and stores are subject to whatever our alias analysis does.

These loads occupy a middle ground: they cannot float and rematerialize anywhere (as a pure op could), but alias analysis is also too weak to do useful things in many situations, e.g. when the GVN might occur across a callsite. We'd still like to reason about the fundamental implication of readonly on its own: once any load to the address has occurred (at an original location that hasn't been code-motioned, etc), and if we continue past that point (no trap), then readonly itself implies that the loaded value will never change -- so we can rewire subsequent identical loads to use the original value.

This makes the sequence

    v2 = load.i32 readonly v1
    call fn0()
    v3 = load.i32 readonly v1

properly GVN v3 onto v2.

Addresses the issue observed in #14683 and discussed in this Zulip thread.
