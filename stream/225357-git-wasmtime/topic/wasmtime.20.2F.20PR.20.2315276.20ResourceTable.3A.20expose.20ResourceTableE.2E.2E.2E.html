pchickey edited PR #15276:

TableEntry is now pub ResourceTableEntry, with pub methods as getters to its contents. pub ResourceTableEntryMut<'_> is used as a wrapper for &mut ResourceTableEntry that allows keeps the assurance that internal parent/child invariants can't be broken by a mem::swap.

To aid debugging the ResourceTable, TableEntry contains the core::any::type_name<T>() of an entry. This adds 2 words (16 bytes) of overhead to each TableEntry, but this debugging concern has come up repeatedly over the years, so my personal judgement is that this is an acceptable cost.

ResourceTable::iter_mut has been changed to have Item = (u32, ResourceTableEntryMut<'_>) and new ResourceTable::iter is the same iterator with Item = (u32, &ResourceTableEntry) for immutable access. Both iterators will never yield a tombstone, which is an internal implementation detail, and ensures that .iter{_mut}().count() == .len(). ResourceTable::iter_entries and iter_children have also been updated to yield those types as well.

This makes sense to me, and I am not opposed to doing this, but perhaps somebody else could weigh in on this before we commit to the path of storing type name strings in all dynamic values?

Personally, if I wanted to iterate the contents of a resource table and answer the question of "what resource type is this" for each entry, I'd rather establish a mapping from TypeId to whatever it is that I am looking for, e.g. a &'static str in this case, and then do a lookup using type_id of the Any when e.g. iterating the table entries.

What do you think about:

  1. Since this is only used for debugging, gating the string behind debug_assertions? https://doc.rust-lang.org/reference/conditional-compilation.html#debug_assertions
  2. Instead of storing the type name along the entry, maintain a TypeId -> &'static str map? This could of course be prone to growing without a bound which could be fine especially if only present in debug builds (1.)
