Part of #9402. With the new separate_constant_pool setting on (it's off by default), Cranelift returns each function's constants as a separate blob with relocations. Wasmtime puts them in a .wasmtime.constants section between the page-aligned text and .eh_frame, as alexcrichton suggested. It's enabled with -C cranelift-separate_constant_pool=true.

On AArch64 a constant load becomes an adrp into a fresh vreg and a load from it, as cfallin outlined, with a relocation for each.

riscv64, s390x and Pulley return an error with the setting on, as do cranelift-jit and cranelift-object for a function with constants. Winch ignores it.

With the setting forced on locally, the wast suite and tests/all pass on x86-64, and the wast suite passes on AArch64 under qemu. I haven't run it on AArch64 hardware, macOS or Windows. With it off, .text matches main for the 28 Sightglass modules below. Most of the size change is page padding of the text.

Wasmtime GitHub notifications bot (Nov 19 2026 at 16:47):

cfallin commented on PR #15344:

Thanks for working this out!

That said, I'm not wild about the changes to MachBuffer. We've tried to keep it as minimal as possible, and the "separate constant pool" feels like a glued-on duplication of some kinds of logic (e.g. fixups) and also does not update the informal-proof comments. We should try to avoid making changes to MachBuffer if possible.

Maybe instead we can have a separate buffer just for constants (perhaps another MachBuffer) and then emit into that as well as part of the MachInst emit plumbing?

We already have mechanisms for separate function bodies to have mutually-referring relocations that are resolved by the text-section builder; we could use the same mechanisms to resolve the relocs from the function-body buffers to the constant-pool buffer. That feels more in line with the current design, and less invasive / simplifies things overall.

Thanks for pointing at how calls between function bodies get resolved. You're right about the duplicated fixups and the missing proof comments, and constants as their own bodies fits the existing design better. I'll rework it that way, with each reference a relocation that the text section builder resolves like a call.

One correction on the second MachBuffer: MachInstEmit::emit and x64's AsmCodeSink only receive one &mut MachBuffer. Emit can't reach another without changing that signature or threading state through each backend. Constants also have no labels, fixups or islands, so a second buffer would hold only bytes. Since resolve_reloc has no usable addend, each constant becomes its own labelled body.

Would it be acceptable for MachBuffer to keep a small table of constant references (offset, reloc kind, addend, constant) next to relocs and traps? It would have no fixup or island logic, and the proof comments stay as they are. The alternative is per-backend emit state. That leaves MachBuffer alone but means plumbing it through each x64 and aarch64 emit site. I'd lean toward the table, but I'll do it your way.
