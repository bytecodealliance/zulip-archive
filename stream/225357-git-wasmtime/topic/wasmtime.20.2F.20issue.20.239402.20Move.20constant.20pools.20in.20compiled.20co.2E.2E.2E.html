alexcrichton opened issue #9402:

Today Cranelift's constant-pools are located in the .text section of the executable, typically located after the function itself. While convenient for code generation this exposes a possible attack vector in Wasmtime where it's trivial to put a "gadget" somewhere in memory. For example using a sequence of v128.const it would be pretty easy to assemble "machine code" at the end of a function. In the face of a bug in Cranelift this could make it possibly easier to amplify into a sandbox escape perhaps.

As a defense-in-depth measure we should try to move the constant pools out of the .text section and into a .data or otherwise read-only section. (not writable or executable). This won't be trivial to do due to the fact that relocations from the text section point at the data section and the relocation range may not always be large enough for the entire text section. Regardless though I wanted to file an issue about this idea.

ilyas-mallah commented on issue #9402:

I'd like to work on this. What I have in mind follows @cfallin's idea of returning the constants as a second blob. MachBuffer would get an option to hand back a function's constants separately instead of emitting them after the code, with every constant use becoming a relocation into that blob. Wasmtime then places the blobs in a read-only section after .text, page-aligned so no constant shares an executable page with code.

x64, riscv64 and s390x already reach far enough. AArch64 is the hard part, since ldr literal would have to become an adrp-based load, which costs an instruction and, for float and vector constants, a GPR. I'd benchmark the options with Sightglass before picking one.

With every function's constants in one section, identical constants could also be coalesced across functions (the part @fitzgen moved here from #1385), and constants would no longer ride along in islands, which was part of what made #12968 tricky.

I'd land it as a few small PRs, starting with the buffer support, then a PR each for the x64, AArch64, riscv64 and s390x backends, and finally turning it on in Wasmtime.

A few things I'm unsure about. Should this be a Cranelift setting or something Wasmtime always enables? Would you prefer a separate section or a page-aligned tail of .text? And would you want an RFC first?

ilyas-mallah commented on issue #9402:

I built a prototype to see how this goes. It adds a Cranelift setting, separate_constant_pool, off by default. With it on, MachBuffer hands back each function's constants as a separate blob, with every use a relocation. Wasmtime puts the blobs in a .wasmtime.constants section on the page after .text. It covers x86-64 and AArch64, not yet riscv64, s390x, Winch, cranelift-jit or cranelift-object.

On x86-64 the backend change is 7 lines. The loads stay RIP-relative and only their displacements change. With the setting off, .text is byte-identical to main for the 28 benchmark modules I compiled. With it on, a running wasmtime run process has no v128.const bytes left in executable mappings (3 before, 0 after). The wast suite and tests/all give the same results with the setting on and off.

On AArch64 each ldr literal becomes adrp x16 and an ldr with the low 12 bits. The x16 register is already kept out of allocation as the spill temporary, so the register allocator needed no change. That relies on no emission sequence keeping a live value in x16 across a constant load, which I haven't audited beyond the tests. Under qemu the wast suite and tests/all give the same results both ways. A module that folds 1,200 distinct constants returns the reference values.

Sightglass on x86-64 (28 benchmarks, 100 samples each with perf counters, on a shared desktop) shows nothing measurable. Execution cycles change by +0.09% in the geomean (99% interval -1.49% to +1.41%). An A/A control of the same engine shows +0.19% (-1.21% to +1.61%). Single-threaded wasmtime compile retires 0.006% to 0.032% more instructions (10 runs per module). I have no AArch64 hardware numbers yet. Statically, the 1,431 constant loads in those modules add 5,724 bytes of code, 0.074% of .text.

One cost showed up. .eh_frame has to start on a page, so the constants section is padded to the text alignment. That grows .cwasm files by 0.49% on x86-64 and 5.0% on AArch64, where the alignment is 64 KiB. Putting the constants after .eh_frame would avoid it.

Is x16 fine for the address, or would you want a register from the allocator? And is this enough to start the MachBuffer and x64 PRs, or do you want AArch64 hardware numbers first? I can push the prototype branch if it helps to see the whole change.

This is unfortunately probably not workable as-is, if you are generating separate MachInsts into vcode during lowering: the invariant is that regalloc is free to insert spills/reloads at any point between instructions, and it may use x16 when needed (e.g. to generate a stack-frame offset if the stack frame is larger than what can be reached by the immediate offset in ordinary loads/stores).

Question: do you generate a single relocation that needs both instructions next to each other (i.e. the Reloc handling processes a single 8-byte sequence with a defined form), or are you generating two relocations, for the adrp and the ldr? Depending on the answer I think one or the other of these is the right solution:

  • If two relocs: allocate a temp vreg as the result of the adrp, then use it as the base of the ldr. In other words, just reify what's going on in the ordinary SSA that the regalloc processes. It will do the right thing and ensure the dataflow works.
  • If one reloc: do adrp+ldr as one macroinstruction (one MachInst).

I suspect the former (I know I've seen the separate high/low-bit relocs) and that's the slightly cleaner approach so I'd lean that way by default.
