Hello, I hit this with rustc_codegen_cranelift's experimental unwinding support on aarch64-apple-darwin, where every function's LSDA goes into _TEXT, _gcc_except_tab, but it applies to any frontend putting many data objects in one custom section (for example Rust's #link_section]).

Problem

Currently every data object with a custom section currently gets its own section. A Mach-0 object file can contain at most 255 sections, so emitting more data objects than that into the same custom section fails with "Too many sections".

Changes

On Mach-0, data objects with the same custom section now share a single section, like LLVM does. Individual data objects can still be dead stripped, since the object file uses subsections via symbols. ELF and COFF are unchanged and still get one section per data object.

Two edge cases: using the same section name with different section types or attributes now returns an error rather than emitting two conflicting sections, and zero-initialized data in such a section is written out as zeros, because uninitialized and initialized data can't share a section.

Duplicate

First, this PR addresses the same problem than #14985, but i believe there is a bug:
On macOS, data objects with the same custom section name now share one section. But zero-filled data (define_zeroinit) and normal data get the same cache key, so both kinds can land in the same section. Say the section gets a zero-filled object A (8 bytes), then a normal object B:

  1. A is added as zero-fill. The section's size grows to 8, but nothing is written to its byte buffer.
  2. B is appended at the end of the byte buffer, which is still offset 0.
  3. Result: A and B both point to offset 0. Reading A returns B's bytes instead of zeros.

Testing

  • Added macho_custom_section_is_shared_between_data_objects: defines 300 data objects (half of them zero-initialized) in __DATA,__custom on aarch64-apple-darwin, and checks that the object has a single __custom section of the expected size, with every symbol at its own offset and the expected contents. Without the change this fails: the first zero-initialized object trips the is_bss() debug assertion in object, and without zero-initialized objects emitting fails with Too many sections.
  • Added macho_custom_section_rejects_conflicting_flags, which fails without the change.
  • cargo test -p cranelift-object (debug and release), cargo clippy -p cranelift-object --all-targets and cargo fmt --check pass.

Other test i did:

  • End to end with rustc_codegen_cranelift on aarch64-apple-darwin (on top of cranelift-object 0.137.0): a program with 300 #[link_section = "__DATA,__custom"] statics, 100 of them all-zero and 30 of them AtomicU64, failed to compile with Too many sections: 0x130 before. With the change it compiles, links with ld64 and runs: all values are read back correctly and the atomics can be written. I can share a gist if you would like to run the test.
