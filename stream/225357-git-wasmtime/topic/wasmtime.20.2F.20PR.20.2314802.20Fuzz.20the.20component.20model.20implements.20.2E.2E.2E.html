implements is the one feature WASI 0.3.1 adopted that's still marked as not fuzzed in docs/stability-wasm-proposals.md, so this is an attempt at closing that gap.

This extends the component_api fuzzer so it can import the host function, and export the guest function, through instances annotated with (implements "wasmtime:fuzz/echo@1.0.0"). The host then defines and looks up the functions through those instances and asserts that is_implements sees the annotation. Both the static and dynamic targets go through the same paths.

Locally this ran for 4×20 minutes (~98k inputs) without finding anything. Once this has been running on OSS-Fuzz for a while, I'd like to follow up with a PR to turn implements on by default.

jrandolf commented on PR #14802:

Thinking about your comment more, I don't think there's a meaningful fuzzer to write for implements.

The spec says attributes are ignored by type checking, and in wasmtime they don't affect compilation, instantiation or calls either. inline.rs copies them for the component's imports and exports, types_builder.rs copies them for the items of component and instance types, and after that they're only returned by ComponentExtern.

The only code that interprets them is ComponentExtern::is_implements, which the named_imports bindings from bindgen! use to find the imports to define, and the named WASI imports are built on those bindings. That's host-side code covered by tests. What this fuzzer found was string matching with canonical names, in is_implements and in Linker lookups, which unit tests cover just as well.

So I'd suggest giving implements the same treatment as the component model: a footnote under Fuzzed saying it's metadata that doesn't affect type checking or execution.

If a fuzzer for arbitrary component shapes would help the component model in general, I'm happy to work on that separately, but the work would be in wasm-smith and it would be more general than just implements since wasm-smith doesn't support components yet.
