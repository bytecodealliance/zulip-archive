I've adjusted to have a new opcode instead which creates an invariant that the first stack-allocating-opcode either fails or succeeds and pushes fp/lr, and that way the previous check of 2 opcodes is now a check for 3 possible opcodes. In some sense that doesn't really satisfy the property you're describing, we're still pattern-matching on the output of Cranelift. At the same time though this is such a niche case (accuracy of a stack overflow backtrace on Pulley) that I don't think this is worth all the rigamarole of side tables and things like that. I've tried to document the invariant in abi.rs for the Cranelift backend, does that seem reasonable?
