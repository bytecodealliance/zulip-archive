In #14597, it was noted that on both Pulley and s390x ISAs, Wasmtime does not correctly handle the youngest frame where a stack overflow is detected.

The basic difference between these two platforms and others is that on s390x and Pulley, the frame of the current function is not yet set up when the explicit stack overflow check is done; on other platforms, it is, because there is a small amount of slack in the limit.

So on most platforms (x64, aarch64, riscv64), we can treat the stack-overflow trap like any other, and resolve the PC and FP at the trap site as indicative of function state in the bottommost frame.

But on these platforms, we get a PC in the callee, and an FP still in the caller. We need to resolve this inconsistency by pulling either one or the other "up" or "down" a frame so they are consistent.

I initially tried adding special "frameless PC" support so that we could report the actual youngest frame, without supporting any accesses that would use its FP (since it doesn't have a frame yet). This turns out to break a lot of assumptions, e.g. the ability to get the vmctx from a debug state slot and report what instance the youngest frame belongs to. In essence, it would then propagate complexity upward where callers would have to skip that special/partial frame anyway.

So instead I think it is more coherent to act as if the youngest frame never happened: think of the stack-overflow as happening at the callsite rather than in the callee after the call succeeds. We will thus show a stack-overflow exception at the call instruction that calls a function with a big frame (or any-sized frame that happens to push past the limit and overflow).

This does create its own kind of cross-ISA inconsistency, but IMHO that is more palatable, because the size of frames, and the ABI that implements their storage, is already an ABI- and platform-specific detail anyway. Basically we are saying that for our ABI on s390x and Pulley, because the stack limit has no slack, stack checks logically happen at the call rather than in the callee.

This does still pass the test in #14597: no frame is "skipped", we may just hit overflow at a different arbitrary point on different platforms.

Fixes #14597.
