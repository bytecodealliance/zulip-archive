The perfmap profiling agent opens /tmp/perf-<pid>.map with create(true) and append(true), which follows symlinks. The path is predictable and /tmp is world-writable, so another local user can create /tmp/perf-<pid>.map ahead of time as a symlink to a file owned by whoever runs Wasmtime. When that user then runs with --profile=perfmap (or ProfilingStrategy::PerfMap), Wasmtime appends one line per compiled function to the symlink target with that user's permissions. The function names in those lines come from the module's name section, so part of what gets written is chosen by the module author.

Linux's fs.protected_symlinks=1 blocks following another user's symlink in a sticky directory, but that sysctl is not set everywhere, and macOS has no equivalent. On macOS, with a symlink to a scratch file in place, the target ended up with lines such as 0x104114000 10 x; touch /tmp/pwned.

Passing O_NOFOLLOW makes Engine::new fail with ELOOP in that situation instead of writing through the link. Behavior without a planted link should be unchanged. The jitdump agent writes ./jit-<pid>.dump in the current directory rather than a shared one, so it is left as is.

Testing:

  • New unit test profiling_agent::perfmap::tests::does_not_follow_symlink plants a symlink at the map path and checks that new() returns an error. It fails without the change and passes with it.
  • cargo test -p wasmtime --lib and cargo test --test all profiling:: pass on aarch64-apple-darwin. I was not able to build for Linux locally; O_NOFOLLOW and OpenOptionsExt::custom_flags are available on all unix targets.
