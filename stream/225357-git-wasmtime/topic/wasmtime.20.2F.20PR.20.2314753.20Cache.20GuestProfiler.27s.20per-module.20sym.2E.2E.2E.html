Closes #14752

GuestProfiler::new rebuilds and re-demangles each module's symbol table on
every call, which costs milliseconds for large modules. This builds the table
the first time a profiler includes a module, keeps it on the Module, and
shares it through an Arc with every later profiler.

Changes:

  • ModuleInner gets a profiling_symbols: OnceLock<Option<Arc<SymbolTable>>>
    behind cfg(feature = "profiling"), with a pub(crate) accessor. There is no
    public API change.

  • module_symbols reads the table from that cache. The table-building code is
    moved unchanged into module_symbol_table.

  • GuestProfiler::new adds the library without its table and attaches the
    shared table with Profile::set_lib_symbol_table. Profile::add_lib keys
    libraries by value, so a table carried inside LibraryInfo would be hashed,
    every name included, on each new profile.

  • A unit test profiles the same module twice. It checks that the second
    profiler reuses the first one's table (Arc::ptr_eq) and that both profiles
    name the sampled frame, demangled. Without the cache the test fails.

Measurements, release build, x86_64 Linux, using the reproduction program from
the issue (median of 1000):

Functions Before After, first profiler After, later profilers
1,500 672 µs 695 µs 12.8 µs
10,000 4.60 ms 4.56 ms 79.9 µs

On a real 1.7 MB Rust module with about 1,500 functions, a later new() drops
from 2.36 ms to 16.3 µs (measured with this change applied to wasmtime 43.0.2).

The remaining per-profile cost still grows with the function count, about 8 ns
per function. I haven't looked into where it goes, and it isn't addressed here.

Checked locally: cargo test -p wasmtime --lib profiling; cargo fmt --check;
cargo clippy -p wasmtime --all-targets with no warnings; cargo check -p wasmtime --no-default-features with and without profiling, with and without
runtime. I couldn't run the CLI test suite (tests/all) locally.

andrewl6097 commented on PR #14753:

I think that the issue there would be that Profilers are pretty short-lived things, AFAICT - there's one per time that you profile things, and so different invocations of the guest all get their own Profiler. wasmtime serve, for example, currently makes a new guest profiler on every instance that it creates. So absent a good deal more plumbing, like "create a new profiler using this old one" or "re-use a profiler", both of which then require API changes from consumers to get the benefit.

Happy to drop the test in either case.
