x64: Lower single-source shuffle of distinct operands to one pshufb

Fixes #14848

A shuffle whose mask only selects lanes from one operand got a single pshufb
only when both operands were the same value. With distinct operands it fell
through to vpermi2b or to pshufb + pshufb + por, both of which read the
operand the mask never selects. This adds two rules, ahead of the vpermi2b
rules, that shuffle only the selected operand when every lane comes from one side.

Changes

  • lower.isle: two rules guarded on SSSE3, like the existing shuffle _ a a
    rule:

    • shuffle _ a _ with an lhs-only mask becomes pshufb a;
    • shuffle _ _ b with an rhs-only mask becomes pshufb b.

    ISLE can't prove the new extractors disjoint from the a a rule, so they get
    their own priorities (2 and 1), and the three rules below shift down to 0, -1
    and -2. The twelve rules above are unchanged.

  • lower/isle.rs: shuffle_lhs_only / shuffle_rhs_only extractors. The masks
    reuse shuffle_0_15_mask / shuffle_16_31_mask, which already produce exactly
    the right constant when a mask reads only one side.

  • The SSSE3 guard keeps a target with AVX512VBMI but no SSSE3 on vpermi2b
    instead of a pshufb libcall. No real CPU has that combination, but the
    existing shuffle-avx512.clif target does, so the new VBMI tests are in their
    own file with a realistic target.

Tests

  • isa/x64/shuffle.clif (SSE4.1) and new isa/x64/shuffle-avx512-single-source.clif
    (SSSE3 + VBMI): lhs-only and rhs-only masks over distinct operands. Against
    the old lowering they fail with pshufb/pshufb/por and vpermi2b
    respectively.

  • runtests/simd-shuffle.clif: the same two masks, on every target in the file,
    including baseline x86_64 without SSSE3.

  • All 1378 filetests and the 158 SIMD spec tests (cargo test --test wast -- simd)
    pass. No existing filetest output changes.

Results

i7-1165G7 (AVX512VBMI), single-thread:

wasmtime 49.0.3 this PR
shuffle-false-dep.wat from the issue 3.37 s (3.4 ns/iteration) 0.85 s (0.85 ns/iteration), 4.0× faster
tract wasm_i32_4x1, 512×512 int8 GEMV, vs scalar generic_i32_4x1 in the same build 0.70–0.79× 1.48×

The second row compares the kernel against a scalar kernel in the same run,
which cancels out machine load. The two builds also have different bases (49.0.3
against main plus this PR). In absolute terms, on a single 49.0.3 binary,
changing only that shuffle operand in the module takes the kernel from 56.7 µs
to 27.2 µs.

Some background on how this turned up, plus a clean before/after measurement of the code that found it.

How it was found. I'm porting a translation model (opus-mt, run with tract) to WebAssembly, and wrote an int8 matrix-vector kernel for it: wasm_i32_4x1. Its inner loop runs one i8x16.shuffle per 16 bytes (from i8x16_shuffle::<0, 4, 1, 5, …>(a16, a16), L386), then i32x4.dot_i16x8_s. Under V8 the kernel is 2.8–4.3× faster than tract's scalar generic_i32_4x1. Under Wasmtime, with the same .wasm and the same microbenchmark, it was 15–25% slower than the scalar kernel.

The cause was the shuffle. LLVM emits it with the loop accumulator as the unused second operand, and on this machine (AVX512VBMI) Cranelift lowers it to vpermi2b, which reads that operand, so each iteration's shuffle waits on the previous iteration's add. Changing only that operand in the module, so that the existing shuffle a a rule matches, halved the kernel's time on 49.0.3. This PR does that in the lowering instead.

Before/after on the microbenchmark. The same module throughout (built from the commit linked above, sha256 9b381e03…f9d504), on three Wasmtime builds:

  • stock: release 49.0.3
  • base: this PR's base, dcfbea188d
  • pr: this PR, e08d044365

Both source builds use crates.io regalloc2 0.15.2, with no patches. Each configuration ran 5 rounds, interleaved, rotating the order, pinned to one core, on an i7-1165G7 (load average 1.2–3.1). Medians in ns per call (min–max):

Stock and base also match each other, so the difference comes from this PR alone. The kernel goes from about 0.75× the scalar kernel's speed to about 1.5×. The kernel doesn't quite reach the hand-patched module's 27.2 µs at 512 × 512. That remaining gap is a separate register-allocation spill in the same loop, which I'm reporting to regalloc2 on its own.
