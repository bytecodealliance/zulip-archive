libsmol opened PR #14987 from libsmol:tcp-read-readiness to bytecodealliance:main:

Fixes #14986.

TcpReceiveStream::poll_ready returned tokio's cached read readiness, which tokio only clears once an operation returns WouldBlock. Right after a connection is set up that readiness can already be set although nothing has been received, so a WASIp2 TCP input stream could report ready before any data arrived (details in the issue).

This makes poll_ready peek a single byte instead. poll_peek waits for data, the end of the stream or an error, and when there's nothing to read it clears tokio's readiness and registers the waker as before. poll_read is unchanged.

Testing

  • p2_tcp_streams gains test_tcp_input_stream_should_not_be_ready_without_data, which checks that neither side of a fresh connection is ready, that the client becomes ready once the server writes, and that it's no longer ready after the data has been read. On main it fails in both p2::sync::p2_tcp_streams and p2::async_::p2_tcp_streams, and passes with this change.
  • cargo test -p wasmtime-wasi passes except p3::p3_sockets_udp_connect, which fails the same way without this change in my environment (Linux aarch64 under OrbStack, where the loopback and public addresses end up on the same local interface).
  • cargo clippy -p wasmtime-wasi --all-targets is clean.
  • In an embedder using wasmtime_wasi::p2::add_to_linker_sync, wasi-libc's poll() on an idle accepted connection now waits for its timeout instead of returning 1 at once.
