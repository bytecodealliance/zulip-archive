Fixes #15281.

This PR makes use of the EpochState<T> introduced in #15191 for encapsulation of GC-heap state mutations (for unrooted refs). The idea is that we want to have the same "cannot mutate without bumping the counter" enforced guarantee for all state that could be mutated by Wasm functions, such as their stack frames (i.e., FrameHandles, the subject of the bug above).

The idea is to introduce an enum Running { Yes, No } and hold an EpochState<Running> in the Store. We then change this (to "yes" or "no") on entry/exit to Wasm from the host, and on exit/entry to the host from Wasm (respectively). Ideally we'd actually put "the real Wasm state" inside T, but that's not possible (e.g. the actual machine stack) so instead we have this stand-in.

We assert that when we set it to "yes" or "no", it was previously the opposite state. This way, we should catch e.g. an entry or return path that we forgot about; if we make it to host code and the state is still "running", that's a bug and we'll hit the assert.

The PR puts enter_wasm and exit_wasm invocations at the narrow waist where all Wasm entry/exit should go through in traphandlers.rs. It fixes the hole that led to #15281 as well (namely, exception raise is also a re-entry).

We can then refactor FrameHandle on top of this: rather than keep its own execution-version snapshot and check it, we can use an EpochStateHandle and check its validity.

In theory we can use this framework for other kinds of "views of frozen state" in the future too, potentially.

cfallin edited PR #15358:

Fixes #15281.

This PR makes use of the EpochState<T> introduced in #15191 for encapsulation of GC-heap state mutations (for unrooted refs). The idea is that we want to have the same "cannot mutate without bumping the counter" enforced guarantee for all state that could be mutated by Wasm functions, such as their stack frames (i.e., FrameHandles, the subject of the bug above).

The idea is to introduce a struct WasmState; unit struct that we "mutate" whenever control transitions from Wasm to the host. Ideally we'd actually put "the real Wasm state" inside T, but that's not possible (e.g. the actual machine stack) so instead we have this stand-in -- just a unit value, and a mutation right after the real Wasm state is updated. The PR inserts a hook at all points where Wasm-to-host transitions occur in traphandlers.rs, and fixes the hole that led to #15281 as well (namely, exception raise is also a re-entry).

We can then refactor FrameHandle on top of this: rather than keep its own execution-version snapshot and check it, we can use an EpochStateHandle and check its validity.

In theory we can use this framework for other kinds of "views of frozen state" in the future too, potentially.

(A previous version of this PR had an enum Running { Yes, No } and hold an EpochState<Running> in the Store. We then changed this (to "yes" or "no") on entry/exit to Wasm from the host, and on exit/entry to the host from Wasm (respectively), and asserted that when we set it to "yes" or "no", it was previously the opposite state. This way, we would catch e.g. an entry or return path that we forgot about; if we make it to host code and the state is still "running", that's a bug and we'll hit the assert. Unfortunately, this was too expensive: the action on return from a hostcall back to Wasm both inhibited tail-calls and also kept more state alive, increasing register pressure and causing spills in compiled libcall runtime code in practice.)
