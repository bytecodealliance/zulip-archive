lthibault opened PR #15167 from wetware:lthibault/pasted-text-file-v2 to bytecodealliance:main:

Why: embedders need to bound active filesystem work and retain its backing
content. A native worker can outlive its initiating future, descriptor, or Store.
An idle handle can still access backing content after active work ends. Existing
filesystem APIs do not let embedders attach owners to these independent lifetimes.

This adds two opaque owners:

  • FilesystemOperation retains an admission value through native execution and
    resource-result installation or disposal. P3 streams share one admission per
    session. WasiFilesystemCtx::set_operation_hook and
    WasiCtxBuilder::filesystem_operation_hook configure admission;
    WasiFilesystemCtx::push_descriptor applies the hook to custom descriptors.

  • FilesystemHandle retains backing ownership through shared handles, native
    duplicates made with try_clone, child opens, and directory iterators.
    Native state drops before its owner. Idle handles do not retain admission.

Both are needed for is_same_object(A, B): A admits the operation, while the
worker must retain B's backing owner after B's descriptor disappears. link_at
and rename_at have the same requirement.

Prior discussion: filesystem operation and native handle lifecycle hooks.

Compatibility

File.file and Dir.dir change from Arc<std::fs::File> to
Arc<FilesystemHandle>. Typed raw-Arc uses and native-file trait bounds can
require changes. Borrowed methods remain available through Deref; try_clone
now returns the owner-preserving wrapper. Constructors accept raw files, though
explicit .into() calls can need type annotations. RELEASES.md records the
break. Guest WIT interfaces do not change.

A descriptor sidecar cannot follow escaped raw-Arc clones. An admission hook
cannot retain idle handles or B's independent owner. Private fields would also
break callers; a registry would add tracking machinery. Explicit raw-file or
OS-handle duplication remains the embedder's responsibility.

Validation

Tests cover cancellation, native worker unwinding, child/result handoff,
secondary descriptors, idle duplicates, directory iterators, and terminal P3
streams while the Store remains alive. Native-worker gates establish ordering;
tests do not infer completion from sleeps.

On macOS arm64 with Rust 1.99.1, cargo test -p wasmtime-wasi --locked
passed 171 unit, 227 integration, and 54 documentation tests. Three existing
tests were ignored. P1 and P3-only filesystem suites passed 136 and 145 tests.
WASI all-target Clippy passed with warnings denied; changed tests pass Rustfmt.

All nine negative controls made their targeted test fail. The passing suites ran
after restoring those mutations. Linux, Windows, the full repository CI matrix,
and performance overhead remain unvalidated.

lthibault commented on PR #15167:

Thanks, Patrick. I appreciate the concern about review cost, and have previously familiarized myself with the policy.

Before opening this PR, I looked into the existing filesystem lifecycle mechanisms and prior discussions, then raised the proposed API on Zulip to get design feedback. I didn't receive a response, so I opened the PR hoping to make the proposal concrete.

The motivating problem is that an embedder (Wetware) needs to account for native filesystem work (wetware/ww#713) and backing resources (wetware/ww#266) independently of guest lifetimes:

  • Operation lifetime: Native work can continue after the initiating guest future or Store is gone. The embedder needs to retain an admission/ownership token until that work actually completes.
  • Handle lifetime: Native file and directory handles, including duplicates and handles retained by workers, can outlive their originating descriptors. The backing-resource owner must survive with the actual native handle.

These are distinct lifetimes. In particular, operations involving multiple descriptors (e.g. is_same_object, rename_at) demonstrate why tracking only the initiating operation or descriptor is insufficient.

The patch implements both contracts and includes regression tests for the relevant cancellation and ownership boundaries.

I recognize this is a substantial diff, and I'm happy to narrow or split it if that would make review more manageable. I'm also open to taking a different approach if there's a better fit for Wasmtime's embedder API.

Ultimately, I'm just trying to move the discussion forward and would welcome your thoughts on the right design. If I've overlooked or under-delivered on any part of the AI tool policy, I'm ofc happy to correct that! :)
