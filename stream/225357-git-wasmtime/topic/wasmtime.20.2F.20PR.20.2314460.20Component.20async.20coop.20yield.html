Wasmtime can keep processing ready, high-priority component work without yielding to the async executor. The two tests cover ways this can happen. In the first, a batch of spawned store tasks finishes before a sibling Tokio task gets a turn to send its oneshot result. In the second, cancellation callbacks repeatedly start and cancel new subtasks, keeping the event loop busy while a timer cannot complete.
This change caps the number of event-loop work turns between yields at 128. I chose 128, inspired by Tokio’s cooperative budget, but I’m happy to consider another cap or a different approach.
