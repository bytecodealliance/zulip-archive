ryancbuckley opened PR #15293 from ryancbuckley:fix/switch-i128-jump-table-offset to bytecodealliance:main:

This PR fixes a bug in which Switch jump tables could be incorrect for certain large i128 values.

Before this change, to compute the jump table index (val - first_index) for a contiguous range of cases, Switch::build_jump_table checked if first_index fit in u64 and negated it as an i64 to add in the immediate. In some cases, (i128 switches with first_index in (1 << 63, u64::MAX]), negating first_index as an i64 produces a positive value. This positive value then causes every case in the range to be out of bounds for the jump table. As a result, they are shunted to the default block.

Fun demo: you can see the miscompile in action in my cranelift-based fork of the Rust playground: link, screenshot.

This change ensures that for i128 switch indexes, iadd_imm_s will be used only when the negated 128-bit index fits in i64; otherwise it subtracts the full 128-bit constant with isub.

I'm not sure I understand why this has to be as complex as it is. It seems to me that:

  • We should always be able to use a subtract instructino to produce val - first_index;
  • We can always use an iconst to get the 64 bits that we want for widths <= 64 bits;
  • For the i128 case, we can use iconst if the top 65 bits are zero (i.e., values in [0, 2^63-1]), otherwise we can always use two iconsts and an iconcat as below.

That nicely decouples the computation (a subtract) and the type-conditional/value-conditional case (getting the 64 or 128 bits that we want into an SSA value).

What do you think?
