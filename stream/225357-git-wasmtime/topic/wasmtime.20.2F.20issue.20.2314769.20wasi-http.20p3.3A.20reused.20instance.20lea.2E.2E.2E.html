avkonst opened issue #14769:

A wasi:http/handler@0.3 instance that is reused for many requests leaks handles until it traps, if all three of these are true:

  1. the guest's response sets content-length;
  2. the host reads exactly content-length bytes of the response body and then drops the body without polling it to the end. hyper does this when it serves a response with content-length, so wasmtime serve-style embeddings will hit it;
  3. at least 2 requests are in flight on the instance at once.

If any one of these is false, 300,000 requests run fine on one instance.

The trap is raised while the guest creates the next response, so it looks like resources from earlier responses are never released:

wasmtime Fails after Error
50.0.0-rc.1 ~100,000 requests resource table has no free keys, in the guest's Response::new
49.0.3 ~25,400 requests cannot allocate another handle: store handle limit exceeded, in the guest's BodyWriter::new

Test Case

Repro: https://github.com/avkonst/wasi-repro (./run.sh runs the failing case and the three passing ones). In summary:

  • guest: a wasip3::http_compat component with two routes that differ only in whether the response sets content-length.
  • host: one instance in one Store, with up to N calls in flight, each started with handler::Prepared inside Store::run_concurrent. Each response body is either read to the end (full) or read until content-length bytes have arrived and then dropped (until-length, like hyper).

Extra Info

  • With content-length, wasmtime-wasi-http consumes the guest body with LimitedGuestBodyConsumer (src/p3/body.rs), not UnlimitedGuestBodyConsumer. GuestBody::size_hint is then exact, which is what lets hyper stop after the declared length and drop the body.
  • The guest writes the body and then the trailers from a task that http_into_wasi_response spawns (spawn_local, then BodyWriter::send_http_body). That task, or the stream and future ends it holds, may be what never completes once the host drops the body. If so, it may be partly or wholly a wasip3/wit-bindgen issue and not only a host-side one.
  • Workaround attempt on 49.0.3: polling the dropped body to the end on a spawned host task made the trap less frequent but did not stop it.

Guest

The whole guest, for reference (the host is in the repo):

//! A `wasi:http/handler@0.3` component with two routes that differ only in
//! whether the response carries a `content-length` header:
//!
//! - `GET /with-content-length`
//! - `GET /without-content-length`

use bytes::Bytes;
use http::header;
use http_body_util::Full;
use wasip3::http::types::{self, ErrorCode};
use wasip3::http_compat::{http_from_wasi_request, http_into_wasi_response};

wasip3::http::service::export!(Guest);

struct Guest;

impl wasip3::exports::http::handler::Guest for Guest {
    async fn handle(request: types::Request) -> Result<types::Response, ErrorCode> {
        let request = http_from_wasi_request(request)?;
        let body = "hello\n";
        let mut response = http::Response::new(Full::new(Bytes::from_static(body.as_bytes())));
        if request.uri().path() == "/with-content-length" {
            response
                .headers_mut()
                .insert(header::CONTENT_LENGTH, body.len().into());
        }
        http_into_wasi_response(response)
    }
}
