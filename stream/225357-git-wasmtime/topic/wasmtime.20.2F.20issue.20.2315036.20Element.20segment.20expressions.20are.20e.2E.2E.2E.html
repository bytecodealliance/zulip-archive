The spec's instantiation evaluates the element expressions of every segment before running any active segment's table.init, so a trapping expression should leave imported tables untouched.

Fixing this in my opinion is going to need to be balanced with implementation complexity. This is a vanishingly niche use case which in theory shouldn't come along with a large implementation burden. Nevertheless I figured it's worth opening here.

po-nuvai edited a comment on issue #15036:

Hi, I'd like to work on this issue. I have an implementation idea and would appreciate your feedback before opening a PR.

If an active element segment contains an expression that may trap (currently only struct.new* / array.new*, as identified by ConstOp::may_trap()), my proposal is to handle it like a passive segment during module initialization:

  1. When reading the module, allocate a hidden passive segment slot that cannot be accessed by WebAssembly code (i.e., don't add it to passive_elem_map).
  2. Evaluate its values along with the other passive segments, before performing any active segment writes to tables. This ensures that if evaluation traps, imported tables remain unchanged.
  3. Later, process it in the normal active-segment order, copy its contents into the target table (similar to table.init), and then free the temporary slot (similar to elem.drop).

Segments that cannot trap (ref.func, ref.null, ref.i31, global.get) would retain the existing fast path, so normal modules would be unaffected.

I have a small local prototype, and the first test case from the issue passes. For the second test case, I suspect the expected trap message might be incorrect: casting an empty slot to (ref i31) produces a "cast failure" rather than "null reference". Replacing the cast with a ref.is_null check makes the test pass.

I haven't run the full test suite yet.

Does this approach sound reasonable? I'd appreciate your feedback on the design before I proceed with a PR.
