Gelbpunkt edited PR #14770:

Since we store I128 in vector registers, we perform loads into vector registers and use vector stores to implement atomic store. This is different from the other backends, which use "regular" atomic load and store instructions from GPRs, which also exist on s390x in the form of LPQ and STPQ. However, s390x differs from the other supported ISAs: its ABI mandates that i128 must be passed indirectly rather than in a pair of GPRs. Using the value of an i128 parameter will generate a load of the value from memory via gen_load (and analogous for gen_store when an i128 is returned), which only gets one Reg to generate the load into - and it will only fit in a VR. Therefore, it makes sense to always keep our i128s in VRs. This also makes sense for atomic_rmw later, where vector operations will generally let us perform the modifications more efficiently than on pairs of GPRs. Therefore, we keep our i128s in vector registers and only move them to GPRs when absolutely necessary (e.g. for CDSG).

This was suggested by @theotherjimmy in yesterday's Cranelift meeting (thanks!).

I've verified that the atomic load/store part of the atomic-128 runtest passes on s390x in qemu-user and on z15 in a z/VM environment, but since the atomic-128 runtest also requires atomic_cas (which I have implemented and will PR as a follow-up) and atomic_rmw (WIP), it cannot be enabled on s390x yet.
