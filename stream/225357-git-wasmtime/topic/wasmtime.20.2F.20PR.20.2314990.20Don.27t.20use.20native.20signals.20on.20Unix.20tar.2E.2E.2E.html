aofusa opened PR #14990 from aofusa:fallback-unsupported-unix-signals to bytecodealliance:main:

On Unix targets where crates/wasmtime/src/runtime/vm/sys/unix/signals.rs has no code for reading and
updating the signal context, such as all NetBSD targets and OpenBSD/aarch64, building wasmtime fails
with compile_error!("unsupported platform").

This changes build.rs to only enable has_native_signals on Unix for the (OS, architecture) pairs
that signals.rs supports. Other Unix targets now build and behave like platforms without native
signals: signals-based traps are turned off, and compiled code performs explicit checks instead.
Nothing changes for targets that build today.

Changes:

  • crates/wasmtime/build.rs: add has_unix_signal_handler, a list of the supported pairs, and use
    it when computing has_native_signals. Only architectures with a Cranelift backend are listed,
    since has_native_signals already requires one.

  • signals.rs: comments next to the two compile_error!s pointing to the list in build.rs.

  • CI: a cargo check job for x86_64-unknown-netbsd, next to the existing FreeBSD one.
  • docs/stability-platform-support.md: a short note on this behavior.

Testing

  • For all 331 targets from rustc --print target-list, I compared has_native_signals before and
    after this change, for each combination of the std and custom-native-signals features. It only
    changes from true to false on Unix targets with a Cranelift backend that signals.rs doesn't
    support (38 targets), and all of them fail to build without this change.

  • macOS aarch64: cargo fmt --all -- --check, cargo clippy --workspace --all-targets --features p3,component-model-async with -Dwarnings, cargo test -p wasmtime.

  • Linux aarch64 (VM): cargo test -p wasmtime with -Dwarnings.

  • x86_64-unknown-netbsd, cross-checked from macOS, matching the new CI job: cargo check fails with
    unsupported platform without this change and passes with it, with -Dwarnings. Also
    cargo check -p wasmtime --no-default-features --features runtime,std,pulley.

  • NetBSD 10.1 aarch64 (VM): cargo check -p wasmtime fails without this change and passes with it.
    cargo test -p wasmtime --lib passes (tests that JIT code need paxctl +m on the test binary,
    because of NetBSD's PaX MPROTECT). A small test program that checks traps (out-of-bounds memory
    access, division by zero, integer overflow, unreachable, bad float-to-int conversion,
    call_indirect to null, with the wrong signature and out of table bounds, stack overflow), fuel,
    epoch interruption, async with fuel yielding, and host function errors passes with both Cranelift
    native code and Pulley, with and without memory guard regions. The same program confirms that
    native signals are disabled at compile time on this target.

  • OpenBSD 7.9 aarch64 (VM): main doesn't build with the packaged Rust 1.94 for unrelated reasons, so
    I applied the same build.rs change to Wasmtime 47.0.4 (MSRV 1.94). cargo check -p wasmtime
    fails with unsupported platform without the change and passes with it, and native signals are
    disabled at compile time. Running Wasm on OpenBSD/aarch64 still has separate issues that I didn't
    look into here: native code hits SIGILL at the first instruction of the compiled function, and
    synchronous Pulley calls crash in the interpreter. veil runs Wasm there with Pulley, async calls,
    and a custom stack creator that maps fiber stacks with MAP_STACK.

  • veil, which vendors Wasmtime 36 with a similar patch: with
    the equivalent build.rs change applied to Wasmtime 36.0.19, veil's Proxy-Wasm end-to-end tests
    pass on NetBSD aarch64.

The NetBSD and OpenBSD VMs have Rust 1.96 and 1.94 from their package collections, which are older
than the MSRV, so I used --ignore-rust-version there. With these versions rustc also reports
unfulfilled #[expect(dead_code)] lints in cow.rs and sync_std.rs with
--no-default-features --features runtime,std,pulley; the same warnings appear with Rust 1.96 on
macOS without this change, so they're not related.

I didn't test running on NetBSD x86_64, only the cross check.

    instruction of the compiled function), so I can't validate signal handling there yet.
