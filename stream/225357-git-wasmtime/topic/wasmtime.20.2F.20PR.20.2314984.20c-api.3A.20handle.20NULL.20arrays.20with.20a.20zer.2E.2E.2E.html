netliomax25-code opened PR #14984 from netliomax25-code:c-api-wasi-null-slices to bytecodealliance:main:

wasi_config_set_argv and wasi_config_set_env build their slices with std::slice::from_raw_parts directly on the caller's pointer and count. With a count of 0 and a NULL array this is undefined behavior in Rust, since from_raw_parts requires a non-null pointer even for an empty slice. The C++ wrapper hits it with WasiConfig::argv({}) or env({}), because data() of an empty std::vector is NULL, and a debug build of the C API aborts with:

unsafe precondition(s) violated: slice::from_raw_parts requires the pointer to be aligned and non-null

The rest of the C API already goes through crate::slice_from_raw_parts, which returns an empty slice when the length is 0, so these three call sites now use it too. They were the only remaining direct slice::from_raw_parts calls on caller-provided pointers in crates/c-api/src.

I added a WasiConfig.EmptyArgvEnv test to crates/c-api/tests/wasi.cc. It aborts at wasi.rs:72 without the fix and passes with it, and the full C API test binary (147 tests, Debug, -DBUILD_TESTS=ON) passes on macOS aarch64.
