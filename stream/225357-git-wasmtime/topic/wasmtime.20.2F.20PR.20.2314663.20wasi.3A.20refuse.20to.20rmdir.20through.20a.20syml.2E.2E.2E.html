With a trailing slash, remove_dir resolved a symlink to its target
directory and then tried to remove . there, failing with EINVAL
(EACCES on Windows). Linux fails with ENOTDIR instead, since rmdir
never removes a directory through a symlink, while macOS and FreeBSD
remove the target and leave the symlink dangling. Follow Linux: it's
the more conservative choice, and the one applications most likely
expect.

The symlink is still resolved within the preopen first, so one that
escapes, dangles or names a file fails as before. FreeBSD's
unlinkat(RESOLVE_BENEATH) fast path now skips trailing slashes, since
that kernel removes the target.

Yeah, makes sense. I checked on Linux, and rmdir gives ENOTDIR for a symlink with a trailing slash no matter what it points to (a directory, a file, nothing, .. or /). It never touches the target. I'll drop the line.

One knock-on effect: upstream wasi-testsuite asserts that rmdir("parent.cleanup/") is NotPermitted, where parent.cleanup links to ... This behavior to remove the underlying dir does appear to match a strict reading of POSIX and is the same behavior macOS uses. Still, I think it's pretty obviously bad to leave the symlink broken which would also be required by this reading (and is what macOS implements).

With this change it's NotDirectory instead, like Linux. I'll send a PR to wasi-testsuite to accept either, so the next submodule bump doesn't break. Happy to make the test require NotDirectory if you'd prefer but allowing POSIX feels prudent.
