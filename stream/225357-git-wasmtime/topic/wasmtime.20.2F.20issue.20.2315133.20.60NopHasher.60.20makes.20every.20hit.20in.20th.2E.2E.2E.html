Test Case

subtype-cache.zip, which holds subtype-cache.wasm, its text form subtype-cache.wat, and gen.py, which writes the text.

The module defines, in one rec group, 38 non-final struct types and 425 final subtypes of them, weighted toward a few supertypes the way a compiler's casts go to a few AST and type classes. Its run export applies ref.test to an instance of each subtype against that subtype's supertype, 100,000 times: 42.5 million tests. Every test misses the exact-type fast path, so each one calls the is_subtype libcall, and after the first round each one is answered from the store's subtype_check_cache.

Steps to Reproduce

  • wasmtime run -W gc=y --invoke run subtype-cache.wasm
  • Time it. It prints 42500000.

Expected Results

A test whose answer is in the cache should cost the libcall plus one hash-map lookup of a u64: a few nanoseconds.

Actual Results

The run takes 3.0 s on wasmtime 50.0.0, about 70 ns per test.

With the change to NopHasher::finish below, the same module takes 0.28 s. I measured that on 50.0.1 embedded in our runtime, where the unchanged 50.0.1 takes 3.1 s.

Versions and Environment

Wasmtime version or commit: 50.0.0 (the CLI); 50.0.1 (the wasmtime crate, for the comparison with the change). 48.0.5 has the same code, and its CLI takes 4.4 s.

Operating system: NixOS 26.11, Linux 6.18

Architecture: x86_64 (AMD Ryzen 9 9955HX)

Extra Info

Cause. StoreOpaque::is_subtype_cached keeps subtype_check_cache: HashMap<u64, bool, NopHasher>, keyed by (sub << 32) | sup, and NopHasher::finish returns the key as the hash. hashbrown takes a key's starting bucket from the hash's low bits and its 7-bit tag from the top 7 bits. For this key:

  • The tag is bits 25–31 of the subtype's VMSharedTypeIndex, which are 0 unless the engine has more than 2^25 types. Every full slot in a probed group matches the tag, so a lookup compares keys slot by slot.
  • The starting bucket comes from the supertype's index alone, so every pair with the same supertype starts probing at the same group, as do supertypes whose indices are equal modulo the table size.

A hit then walks the cluster around its supertype. TraceInfos::map (HashMap<VMSharedTypeIndex, TraceInfoLoc, NopHasher>) has the same constant tag.

Change. Mixing the key in NopHasher::finish, here with Murmur3's 64-bit finalizer:

fn finish(&self) -> u64 {
    let mut h = self.0;
    h ^= h >> 33;
    h = h.wrapping_mul(0xff51_afd7_ed55_8ccd);
    h ^= h >> 33;
    h = h.wrapping_mul(0xc4ce_b9fe_1a85_ec53);
    h ^= h >> 33;
    h
}

A multiplication alone would not be enough for this key: the low bits of a product depend only on the low bits of its input, which are the supertype index, so pairs would still start at their supertype's bucket. Using hashbrown's default hasher for the two maps would also work.

Effect on a real program. We run a compiler written in a WasmGC language (Zena) on wasmtime. A compile makes about 67 million subtype checks over about 425 distinct pairs. Because the probe lengths depend on the exact type indices, its compile time also moved with changes that only shifted them. On 50.0.1, two builds of the compiler took 17.0 s and 24.4 s on the same input, though the second does less work. With the change above they take 15.6 s and 14.9 s, with byte-identical output. On 48.0.5, the first build became as slow as the second, 23.8 s against 14.4 s, when we loaded the second build's driver module into the same engine before it, which only shifts the engine's type indices.

This is separate from #13484, which would make the cache unnecessary.
