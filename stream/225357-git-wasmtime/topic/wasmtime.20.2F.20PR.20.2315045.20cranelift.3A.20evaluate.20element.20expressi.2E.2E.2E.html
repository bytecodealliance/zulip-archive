Motivation

Per the WebAssembly Core Specification on module instantiation, all element segment expressions must be evaluated before applying any active segment's table.init.

Previously, during Cranelift module startup code generation (crates/cranelift/src/func_environ.rs), module_initialize_table_with_segment evaluated element expressions and immediately wrote them to the target table via translate_table_set. If a subsequent element expression trapped (e.g. allocation size too large, division by zero, or null reference), earlier table writes had already mutated imported tables, violating the specification invariant that a trapping expression must leave imported tables untouched.

Solution

This PR splits active table segment initialization in crates/cranelift/src/func_environ.rs into two distinct phases:

  1. module_prepare_table_segment:

    • Evaluates segment offset expressions.
    • Performs bounds checks before mutating any state.
    • Pre-charges bulk operation fuel.
    • Evaluates all element expressions / function references into Cranelift SSA values (ir::Value).

  2. module_apply_table_segment:

    • Iterates over the prepared element values and writes them to the target table via translate_table_set.
    • Post-charges bulk operation fuel.

During compile_module_start, all active segments are prepared in Pass 1 before any segment applies table writes in Pass 2. If any element expression traps, execution aborts before any table mutation occurs.

Includes regression test in tests/misc_testsuite/issue15036.wast.

Closes #15036
