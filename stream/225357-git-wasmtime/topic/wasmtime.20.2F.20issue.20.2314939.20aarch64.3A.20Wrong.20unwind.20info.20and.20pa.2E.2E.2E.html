The .xdata entry for function[1] is at offset 0x8, and its unwind codes
are cc 01 e1 81:

  • cc 01 is save_regp_x x19, x20, [sp, #-16]!, but the prologue saves x19, x26.
  • There's no end (e4) code. The next function's header (3a 00 00 30) follows immediately.
  • The stack-limit check at 0x28-0x38 has no codes, so the codes don't map one-to-one to prologue instructions.

<details>
<summary>LLM summary, if helpful</summary>

All three are in cranelift/codegen/src/isa/unwind/winarm64.rs:

  • preserve_all panic: Windows arm64 unwind codes can only describe
    saves of x19-x28 and d8-d15 (short of save_any_xreg), and
    create_unwind_info panics on anything else. preserve_all saves
    x0-x17 too, and Wasmtime uses it for the guest-debug breakpoint
    trampoline.

  • Non-consecutive pair: the prologue saves callee-saved registers two
    at a time in sorted order, and regalloc2 doesn't hand them out
    consecutively, so stp x19, x26 happens. The two SaveReg records are
    merged into one save_regp_x, which can only express x(N), x(N+1), and
    the second register is dropped. An SEH unwinder would restore x20 from
    x26's slot and leave x26 alone.

  • No end code / not one-to-one: emit writes only the prologue
    codes, never end, and no nop codes for prologue instructions that
    don't change unwind state (bti c, the stack-limit check, the tail-call
    frame move, multi-instruction SP adjustments). The format requires both
    for unwinding from inside a prologue. Wasmtime's own unwinding uses
    frame pointers, so this affects only SEH-based tools (debuggers, ETW,
    RtlVirtualUnwind). None of this was tested on Windows.

</details>
