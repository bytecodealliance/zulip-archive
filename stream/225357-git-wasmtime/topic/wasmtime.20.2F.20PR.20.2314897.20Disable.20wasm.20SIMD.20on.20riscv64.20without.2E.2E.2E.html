Follow-up to #13959 and #14524. Compiling a module that uses v128 for riscv64 without the V extension panics in the backend. wasmtime compile --target riscv64gc-unknown-linux-gnu with default flags hits it, and so does a native host without V. #14524 fixed the memcpy half of #13959, and this is the other half Alex mentioned in that issue.

On such targets SIMD and relaxed SIMD are now off by default, so these modules fail validation with "SIMD support is not enabled". Turning either one on explicitly makes Engine::new fail. The check isn't in compiler_panicking_wasm_features because that runs in Config::validate, before native ISA flags are detected.

I think this might be best to invert a little bit with the way features work:

  • In Config::compiler_panicking_wasm_features the compiler.supports_wasm_simd() line will want to list the simd/relaxed-simd features as panicking if that's false
  • Later in this function build_compiler this wouldn't mutate features but would double-check that if the compiler doesn't support simd that simd/relaxed-simd are both disabled.

That way it'll be off-by-default for the relevant targets, and if users explicitly-opt in they'll still get an error.

Wasmtime GitHub notifications bot (Oct 21 2026 at 14:44):

:speech_balloon: ilyas-mallah created PR review comment:

Makes sense to route it through the same path as the other unsupported features, so I moved it into the panicking set in https://github.com/bytecodealliance/wasmtime/commit/6cb80301aa1cc5543692b1db2fcb855752189832.

The one difference is that Config::validate calls compiler_panicking_wasm_features before a compiler exists, so it takes a compiler_supports_simd flag instead of the compiler. validate passes true. build_compiler repeats the check with compiler.supports_wasm_simd() once the ISA flags are known, and Engine::new takes its features from that second pass.

If you'd rather it take the compiler directly, an Option<&dyn Compiler> works too, but it needs cfg gates in config.rs.
