TastyCZ opened PR #14999 from TastyCZ:cranelift-volatile-memflag to bytecodealliance:main:

This adds the volatile MemFlag discussed in #1598: a load or store with this flag happens exactly as written. Nothing removes it, merges it with another access, or folds it into another instruction.

Today a frontend has no way to ask for that. At opt_level=speed, alias analysis removes the first of two stores to the same address, replaces the second of two loads with the first, and forwards a stored value to the following load; an unused notrap load is not emitted at any opt level. rustc_codegen_cranelift needs the flag for read_volatile/write_volatile (rust-lang/rustc_codegen_cranelift#1715).

What the flag does in each pass:

  • inst_predicates: a volatile load has a side effect, so it is lowered even when unused, and it is never pure for the egraph (no GVN, LICM or rematerialization).
  • alias analysis: a volatile access is never replaced by a known value, never removed as an idempotent or dead store, never the source of a known value, and never makes another store dead. It is also treated as a fence: it observes every earlier store and clears what is known about memory, so nothing is forwarded across it.
  • lowering: a volatile load is never sunk into its user's memory operand (which could change its width or read it twice), on every backend.
  • verifier: rejects volatile together with readonly or can_move.

The flag takes the unused bit 4 of MachMemFlags, prints and parses as volatile, and is listed with the other memory flags in cranelift/docs/ir.md. Accesses without it compile as before.

Tests: new filetests alias/volatile.clif, egraph/volatile.clif, verifier/volatile.clif, isa/x64/volatile-no-sink.clif and isa/aarch64/volatile-no-sink.clif, plus a print/parse round trip in memflags.rs. With volatile on each access, the four functions from the issue keep every load and store at opt_level=speed and none.

One thing to look at in review: the fence treatment in alias analysis is the conservative choice, since it also stops forwarding between non-volatile accesses on either side of a volatile one. I'm happy to narrow it if you'd prefer volatile accesses to only stay apart from each other.

Closes #1598

I would remove the "never folded into another instruction, so its count and width stay as written": the way that we do load-folding does preserve count (we only do it for singly-used loads) and width (modulo some bugs we've had, we never extend width). We also have an analysis that ensures that the load doesn't move across any other side-effecting op.

So given that, in principle I think it should be perfectly fine to fold a volatile load as we do any other: it is semantically invisible both to the current program and to other concurrent readers/writers on the memory (and to the memory hardware itself).
