jrandolf opened PR #14919 from jrandolf:wasi-config-named-imports to bytecodealliance:main:

Components importing wasi:config/store under a label couldn't be linked with wasmtime-wasi-config. Its bindings are private, so embedders couldn't do it themselves either. This adds add_named_to_linker, following the named-import support in wasmtime-wasi (#14275).

wasmtime-wasi-config now depends on wasmtime-wasi (it was a dev-dependency) to share its NamedId. That grows its dependency tree from 77 to 151 crates, so I'd appreciate a second opinion on whether that's the right way to share it.

Part of #14858

<details>
<summary>LLM summary of the changes</summary>

API

  • WasiConfigNamedView maps a NamedId to the WasiConfig context to use.
  • Interface has ConfigStore.
  • add_named_to_linker adds every labelled import of wasi:config/store that the component has, asking lookup for each one's id.

Implementation

The bindings get named_imports for wasi:config/store. Each named method looks up the context for the id and calls the existing implementation.

Dependency

wasmtime-wasi moves from dev-dependencies to dependencies, for NamedId (a usize newtype) and WasiCtxNamedView (a one-field wrapper). It's used without default features, but its non-optional dependencies such as tokio still come along. Cargo.lock doesn't change.

Interaction with #14873

#14873 changes the signature of the add_named_to_linker lookup. Whichever of the two lands second needs to port this function, which is mechanical.

Test

config_named_imports runs a new guest program with two labelled wasi:config/store imports, each with its own variables, and checks that the labels get separate contexts.
