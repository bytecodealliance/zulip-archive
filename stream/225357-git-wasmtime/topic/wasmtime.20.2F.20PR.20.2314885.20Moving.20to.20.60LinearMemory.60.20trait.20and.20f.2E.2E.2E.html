Following up on the discussion on #10740 I propose a rework of the memory API that centralizes the requirements for linear memory implementation in the public LinearMemory trait.

The core challenge is resolving the issue from #10740 -- custom memories did not work with the CoW mechanism. This is because the code mounting memory images was hardwired to the internal mmap implementation. The idea is to move the responsibility for supporting CoW into the LinearMemory implementation with the new function init_from_image. It receives an opaque public MemoryImage that informs the implementor where it needs to be mounted (offset and length). The predicted path is that a memory that supports mapping the image over it (backed by mmap) calls the map_at callback and acknowledges that the pages required for the image have been remapped (returns true). If this is not supported, the implementation (default) returns false and wasmtime abandons CoW mapping in favour of a full copy of the data pages. The MemoryImage struct also exposes the underlying bytes of the memory and equality semantics, so custom implementors can, in theory, implement their own lazy copying or their own pooling.

The second change is that LocalMemory was holding an Option<MemoryImageSlot> to support the StaticMemory and pooling allocators. It also manually called the set_heap_limit on the slot during grow. I did two things:

  1. The MemoryImageSlot is now owned by the StaticMemory and LocalMemory only records if the memory needs to be initialized from an image (for the purposes of needs_init() required by instantiation code). This makes it so that LocalMemory depends only on the LinearMemory implementation and needs no knowledge of the pooling allocator machinery.
  2. LinearMemory now has the Any supertrait. This is a) required so that the pooling allocator can get the inner Box<dyn LinearMemory> from LocalMemory and unwrap it to what it knows to be StaticMemory and recover the MemoryImageSlot, b) useful in the potential future where we add the ability to retrieve the memory impl from an instance, as a custom memory could be downcast from Box<dyn LinearMemory>.

== Overview of code changes

Public API changes:

  • LinearMemory gets init_from_image
  • MemoryImage (arg to the above) is public

These are non-breaking: existing LinearMemories will not support CoW, but instead of crashing they'll just force wasmtime to copy.

Removed:

  • the internal RuntimeLinearMemory trait
  • the LinearMemoryProxy that wrapped a Box<dyn LinearMemory> and provided the RuntimeLinearMemory impl

This functionality is now centralized in the LinearMemory trait.

The MmapMemory was refactored to accommodate the changes, it relied on RuntimeLinearMemory. Now it uses the standardised path through init_from_image to map a CoW image, although with a hatch through an internal MemoryImage::vm() to keep all of the mmap code as it was with the nice static Mmap types that were already there. Technically one could get rid of the vm() function, but changing all the mmap code felt like more hassle than it's worth.

MemoryImageSlot is now only used by the pooling code. In fact, its definition could be gated behind #[cfg(feature = 'pooling-allocator')]', but that would trigger a whole cascade of cfgs because a lot of use` statements become dead code with the feature disabled and trigger warnings. I wasn't sure if we want those cfgs splattered everywhere, but I can introduce them if we do (judgement call for the code owners).

I fixed what I think was a bug (see Zulip discussion #wasmtime > Custom memory creators for host memories @ 💬) in create_memory where custom memory creators were bypassed and the default creator was always used. This mean Memory::new always created a default memory and not a custom one. I added a regression test for that.

The new functionality is tested in tests/all/memory_creator.rs with focus on CoW behaviour for custom memories. The new public MemoryImage is thoroughly tested in unit tests in runtime/memory.rs. I also added a few tests I felt were missing: MmapOffset (to make sure the bounds checks are correct, since they must be for unsafe code to be sound) and a few tests for LocalMemory growth.

I also tried to make the LinearMemory safety documentation more useful for implementors. Organised the requirements into bullets so that an implementor can reason about their safety contract and "tick-off" the requirements.
