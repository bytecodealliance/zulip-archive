Fixes #13959.

Small constant-length copies can generate i8x16 loads and stores even when the target does not support them. On RISC-V without vector support, this causes a compiler panic, including when WebAssembly SIMD is disabled.

This checks whether the target supports the vector type before using it in the shared inline-copy helper, falling back to scalar loads and stores otherwise. The RISC-V check uses the configured vector register size and shares the element-type checks with lowering.

Adds a regression test that cross-compiles a 16-byte memory.copy for RISC-V with both has_v and WebAssembly SIMD disabled.

:speech_balloon: dotcom07 created PR review comment:

I extracted this helper from the existing element-type checks in ty_supported().
In #6266, vector lowering was changed to use the register-size check instead of an explicit has_v check. As noted in [this discussion], V implies Zvl128b, but not the other way around.

Adding a mandatory has_v check to this shared helper would also change existing lowering behavior, rejecting vector types previously accepted with Zvl enabled and V disabled.

One concrete example is a processor implementing Zve32x with Zvl128b: it can support i8x16 loads and stores without implementing the full V extension.
However, the backend does not currently model Zve extensions explicitly, so the register-size check alone does not capture all element-width and instruction restrictions. I'd be interested in exploring explicit Zve support as a separate follow-up.
