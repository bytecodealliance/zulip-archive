We previously accepted arbitrarily large requested alignments for explicit stackslot entities in CLIF. We even tried to give the user this alignment relative to the start of the frame. But in a given ABI, if the stack is only N-aligned on function entry, unless we pad it out to get greater alignment depending on the low bits of SP, an M-aligned (M > N) offset from that initial SP is still only N-aligned.

We could do the complicated thing and try to pad to a greater alignment, but it turns out that we don't need to, at least in Wasmtime. Most things (including ValRaw!) only need 8-alignment. x64, aarch64 and riscv64 can support 16-alignment because their native-ABI stacks are 16-aligned. s390x's stack is only 8-aligned, however, but per above, that's fine for core Wasmtime uses. Stack-switching still requests 16-alignment for a u128, so we'll either need to not do that, or do something fancier, on s390x if/when we support stack switching there. For now, this aligns the Cranelift checks with what we can support in reality, and cleanly rejects invalid requests.
