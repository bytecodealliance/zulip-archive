alexcrichton commented on PR #15312:

At this time Wasmtime doesn't have a requirement of a formal proposal phase for a PR, but all PRs are subject to maintainer review. Reviews can often poke on the fundamentals of a PR as I'm doing here, however.

One thing I can also perhaps clarify here though is that there's two aspects here. One is the semantics of actually running WebAssembly guests, and one is how Wasmtime is compiled itself. The no-std nature here has nothing to do with WebAssembly guests and instead has everything to do with how Wasmtime is compiled itself. For example a no-std Wasmtime build might run a guest that was itself compiled with the Rust standard library compiled down to WebAssembly. The distinction I want to make is that the semantics of WebAssembly and guests are fixed regardless of how Wasmtime is itself compiled (no-std vs not).

it is hard for me to imagine a use case where we would put blocking wasm in the kernel (which is what no-std wasm targets, right?)

An example here is that WebAssembly has defined and fixed semantics for memory.atomic.wait{32,64} and shared memories. No matter how Wasmtime is compiled it needs to uphold those semantics to claim support for the threads proposal. The nature of the guest, whether it's a no-std wasm target or not, only dictates what subset of WebAssembly the guest is using. As a runtime, however, Wasmtime is still tasked with implementing WebAssembly instructions as defined.

Wasmtime does not support all wasm proposals in all configurations in an attempt to support wasm in as many places as possible. For example if you disable the gc Cargo feature of Wasmtime you won't be able to allocate wasm GC objects. That's how threads works right now as well, where if the Cargo feature is disabled then the wasm feature is disabled as well. Wasmtime as a runtime has some leeway to implement things, but we generally require opt-ins for non-standard behavior. For example one non-standard behavior you might want is that memory.atomic.wait* would trap (not panic) when called. That would cause all guests to terminate if they called that, and whether or not that's useful is up to your embedding. Similarly 64-bit atomics could simply trap at runtime to support hosts that don't have 64-bit atomics, but you'd have to ensure that your guests don't ever use that.

why wasm32 and not wasm64?

This is another example of wasm32/wasm64 are a guest toolchain convention, not a runtime concern. Wasmtime implements the memory64 proposal which means it can run either wasm32-compiled or wasm64-compiled guests, but individual wasm instructions, like memory.atomic.wait64, still have defined semantics no matter how the guest is compiled.

Overall it sounds like what you would want is to limit the wasm instructions that a guest can use. It sounds like you ideally want to reject the threads proposal entirely if guests themselves aren't spawning threads. If they're being run in parallel then in theory what you'd want is a guest that doesn't use unsupported instructions. What exactly unsupported instructions fall into this category would be up to you and would be a new invention for your embedding. Wasmtime does not have fine-grained support for wasm instructions like that.

My point is that the conversation here, in my opinion, is about what functionality Wasmtime needs to support in an embedding such as yours, and what happens in the case that a wasm module is loaded that uses unsupported functionality. The answer is not to simply panic because we consider runtime panics as CVEs. The answer probably isn't as simple as "just trap" because that's nonstandard WebAssembly behavior. That's not to say nothing can be done, however, but instead this is where I was intending to start the conversation and take it from here. It's totally ok if you would prefer to not land this support upstream in the meantime, but I want to be clear about the expectations from our side at least.

cfallin commented on PR #15312:

One potential way of squaring the circle here w.r.t. memory.atomic.wait{32,64} is to add new expected "embedder API" functions (see wasmtime-platform.h) and call these. Then your kernel-space embedding can implement them however you like. We would certainly recommend you implement semantics per the spec: minimally probably a spinloop (still has futex semantics, just no CPU yield), or actually yield the CPU if you can do that in your kernel thread.

What Alex is getting at in part is that much of the value of the Wasm platform is that the spec is invariant once a feature is supported, so guest libraries can build on it without Wasm-platform-specific patches. That avoids silent mis-execution bugs, which can be really really pernicious to debug (imagine buying a CPU that executes one particular synchronization instruction incorrectly, then trying to run a standard software stack on top!).
