:memo: rvolosatovs submitted PR review:

Thanks for working on this! Making sure tasks don't outlive their Store makes sense to me, but I think the current structure is heavier than it needs to be. Each request now goes through wasmtime_wasi::runtime::AbortOnDropJoinHandle, DelayedAbortOnDropHandle, a oneshot, a timer task that is always spawned, and a Store-spawned future, plus the Arc<AbortOnDropHandle> references.

Could we use plain tokio types instead, and spawn the timer only when the Store is actually dropped while the task is still running? Something like (LLM-generated):

struct StoreDropGuard {
    abort: AbortHandle,
    grace: Duration,
    rt: tokio::runtime::Handle,
}

impl Drop for StoreDropGuard {
    fn drop(&mut self) {
        if self.abort.is_finished() {
            return;
        }
        if self.grace.is_zero() {
            self.abort.abort();
            return;
        }
        let abort = self.abort.clone();
        let grace = self.grace;
        self.rt.spawn(async move {
            tokio::time::sleep(grace).await;
            abort.abort();
        });
    }
}

let task = tokio::task::spawn(async move { /* … */ });
let abort = task.abort_handle();
let io = Arc::new(AbortOnDropHandle(abort.clone()));
let guard = StoreDropGuard {
    abort: abort.clone(),
    grace,
    rt: tokio::runtime::Handle::current(),
};
store
    .spawn(async move |_| {
        let _guard = guard;
        if let Err(e) = task.await {
            if !e.is_cancelled() {
                debug!(?e, "`send_request` I/O task panicked");
            }
        }
        Ok(())
    })
    .map_err(|e| {
        abort.abort();
        HttpError::trap(e)
    })?;

This would:

  • remove the timer task and oneshot that are currently created for every request,
  • avoid the panic on cancellation, since we never poll the WASI AbortOnDropJoinHandle wrapper,
  • abort immediately if store.spawn fails,
  • capture the runtime Handle up front, since the Store may be dropped outside of a Tokio context.

This still does not address the issue with guest forwarding the body back to the host, though, so it seems like we have to add a way to opt-out of this mechanism for that particular case.
