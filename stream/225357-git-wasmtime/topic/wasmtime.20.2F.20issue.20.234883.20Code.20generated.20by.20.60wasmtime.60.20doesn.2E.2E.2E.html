koute opened issue #4883:

The problem

Currently wasmtime/cranelift (unlike e.g. LLVM which doesn't have this problem AFAIK) doesn't cache-align the loops it generates, leading to potentially huge performance regressions if a hot loop ends up accidentally spanning over multiple cache lines.

Background

Recently we were updating from wasmtime 0.38 to 0.40 and we saw a peculiar performance regression when doing so. One of our benchmarks took almost 2x the time to run, with a lot of them taking around ~45% more time. A huge regression. Ultimately it ended up being unrelated to the 0.38 -> 0.40 upgrade. We tracked the problem down to memset within the WASM (we're currently not using the bulk memory ops extension) suddenly taking a lot more time to run for no apparent reason. Depending on which exact address wasmtime decided to generate the code for memset at (which is essentially random, although consistent for the same code with the same flags in the same environment) the benchmarks were either slow, or fast, and it all boiled down to whether the hot loop of the memset spanned multiple cache lines or not.

You can find a detailed analysis of the problem in this comment and this comment of mine.

Wasmtime GitHub notifications bot (Sep 08 2022 at 17:21):

cfallin commented on issue #4883:

This might be a good starter issue for someone to tackle. The main steps I see this taking are:

  • Convey a notion of "loop header block" to lowered blocks in the VCode. This information can be obtained from the loop analysis, or perhaps more simply and with less overhead, by detecting backedges (branch from higher-index block to lower-index block) when lowering code and marking the target as a header. (The latter is precise for reducible control flow and approximate but pretty good for irreducible control flow.) This would probably best be done somewhere around here and could insert the block index into a set held by the VCode.
  • When we reach a loop header block in VCode::emit, use the stricter loop-header alignment (64 bytes probably?) here rather than the default basic-block alignment, which is 1 byte on x86-64.

If no one else wants to take it, I can do this at some point but I thought I would put this out there first!

zion-sati commented on issue #4883:

Some aarch64 data for this issue, from Apple M1 Max with Wasmtime 50.0.1.

We compile .NET to Wasm (NetWasm) and benchmark on Wasmtime, and loop placement is the largest source of noise we see on this machine: identical loop code moving by a few bytes changes run time by 20 to 30%, which is more than most optimizations we measure. Aligning functions does not help, because the loop moves inside its function.

Minimal repro. The function below is the trial-division loop from our prime search workload (largest prime below a limit, one division a step), written out as Wasm in the shape our compiler emits it. N stores of the argument to globals run before the loops, so each extra store moves both loops 4 bytes later in the function and nothing else changes. Each variant is precompiled with -C cranelift-log2_min_function_alignment=12 and run with wasmtime run --allow-precompiled --invoke run pad.cwasm 10000000; loop head offsets come from wasmtime objdump --addresses. In real code. The same loop in our compiled workload went from 630 ms to 763 ms between Wasmtime 49.0.3 and 50.0.1 with identical loop instructions: 49 emitted return-address signing (pacibz/autibz) by default on macOS and 50 does not, so every function's body sits 4 bytes earlier. Passing -C cranelift-sign_return_address=true to 50 gives the same instructions at the same offsets and the old timing. We see the same pattern elsewhere: a few extra instructions early in a function move three identical string-search loops by 8 to 40 bytes and cost one benchmark about 1.3x, and a LINQ loop that is the same instructions in two builds differs by 1.2x at every function alignment we tried. Compiled with -W epoch-interruption=y, whose checks move code inside functions, those differences disappear or reverse.

The same workload compiled by Rust and by Mono's AOT compiler did not move on that upgrade; their loops have other shapes, so this looks like a property of loop shape and position rather than of one compiler's output.

Happy to time a prototype of loop-head alignment on this machine and on x86-64, with the repro above and our 2,000-case micro suite, if that would help with the code-size and heuristic questions raised in #5004.

zion-sati commented on issue #4883:

Following up with a prototype and measurements, as offered above.

The prototype (branch) adds three Cranelift settings: an alignment, a padding budget and a maximum loop size. It aligns the header of each innermost, non-cold loop. The header's label is bound before the padding is measured, so a jump into the loop from the previous block is still removed.

Code size over benchmarks/all.suite (the span of the function symbols in each .cwasm, so page padding is not counted):

Setting aarch64 x86-64
16 bytes, at most 8 of padding +0.29% +0.17%
32 bytes, at most 16 of padding +0.48% +0.32%
64 bytes, at most 63 of padding +3.33% +2.80%

Execution on x86-64 (Intel Core i5-12600K, P-cores only, Sightglass execution phase, 20 iterations). The same engine library ran with the setting off and on. The geomean is +0.4% at 32 bytes and +0.1% at 16 bytes, leaving out five libsodium and noop benchmarks whose own spread exceeds 10%. A few loop-bound benchmarks gain: wat-bytecode-interp 1.16x and shootout-sieve 1.11x at 32 bytes. A few lose: shootout-minicsv 0.95. Nearly all of the padding sits where the previous block falls through into the loop, so it runs once per loop entry.

Execution on an Apple M1 Max. Alignment removes the placement variance I reported above, but it doesn't pick the fast placement. On current main, the trial-division loop from the repro above ran at 1.00 to 1.22 of its best time across 16 placements with alignment off. It runs at about 1.21 at every 16- and 32-byte-aligned placement.

So on these two machines, a static heuristic like this gives no suite-wide gain, and I won't open a PR. The raw data, per-benchmark results and scripts are here for anyone who wants to try a different heuristic.
