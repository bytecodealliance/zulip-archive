Closes #9572.

This adds Memory::discard(store, start, count), the host API fitzgen sketched in #9572. It zeroes Wasm pages of a non-shared memory and gives them back to the OS where Wasmtime owns the mapping. Like grow and size, it counts in Wasm pages, so a range is always page-aligned. The memory's size and base pointer don't change, and the pages read as zeros if they are touched again. Linear memory can't shrink, so this lets an embedder whose guest allocator frees large spans return that memory instead of holding the guest's high-water mark until the instance is dropped.

The separate memory.discard proposal takes bytes and rounds them to whole pages; taking pages means nothing is rounded and is consistent with grow/size, so that's the approach I took.

How it works:

  • On Linux it calls madvise(MADV_DONTNEED) on the pages. Other Unix platforms map fresh zeroed memory over them, and Windows decommits and recommits them.
  • If the memory was initialized from a copy-on-write image, madvise on Linux would bring back the image's data instead of zeros. So that part gets fresh zeroed memory, and the slot drops the image at its next reset, as resets already do on other platforms. The next instance maps the image again.
  • Memories that Wasmtime doesn't map itself, such as a custom LinearMemory, are zeroed by writing. They read the same afterwards, but no memory is released.
  • Pages out of bounds, or a memory with a custom page size, return an error. Shared memories aren't supported.
  • The C API gets wasmtime_memory_discard and the C++ API Memory::discard, consistent with the rest.

The tests cover each of these cases, including the Linux image case, and a C++ test covers the new binding. I ran the Rust tests on macOS and on x86_64 and aarch64 Linux, and the C API tests on macOS.

This is my first contribution to wasmtime and it's a larger one, so let me know if you have changes or concerns.
