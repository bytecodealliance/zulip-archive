Overall I personally still feel lost on this. For example I feel that there's still two major open questions:

  • How exactly to represent variants? If we go the "everything has a canonical type" route than all the rec-group matching/copying here is dead code and irrelevant.
  • Whether or not to "flatten" more. If we go the route of everything having a canonical type then it seems a bit silly to turn option<u8> into a (ref $option_u8) when passed as a parameter when in the linear memory ABI it's two scalars being passed which should be far more efficient.

These are pretty fundamental pieces of the ABI which I feel are currently unresolved, and I feel that they pretty heavily influence the implementation and what we land here. I'm not opposed necessarily to landing this and moving on that later, but this is 2kloc of new code which is pretty intense IMO and it's only the tip of the iceberg. I find it really hard to retroactively reason about vast amounts of new code when the underlying primitives change, and we've been burned quite a few times by refactoring the design of component-model-async at the spec level and the PR to implement in Wasmtime leaves a lot of vestiges of things that bite us later.

So question for you: what would you like the plan to be on this? Land this now as-is and possibly refactor later? If so what would be the main purpose of landing this in-tree?

So question for you: what would you like the plan to be on this? Land this now as-is and possibly refactor later? If so what would be the main purpose of landing this in-tree?

My goal is to fill out the lifting/lowering from GC objects paths, which I think are the most critical things to shake out and are actually going to look pretty similar regardless anything I can imagine changing about the CM+GC proposal.

It is true that the rec group cloning would largely go away with an "everything has a single canonical type" potential future, but (a) I think that is actually the simplest and most self-contained code here, and (b) it would be replaced by "generate the canonical core types for this CM type" code that actually would be somewhat similar, and similarly self-contained.

I would say there are two primary motivations for landing it in tree, rather than e.g. a bytecodealliance/wasmtime-cm-gc fork:

  1. To make it easier for toolchains to start playing with it and giving us implementation and spec feedback.
  2. To do incremental reviews and build a shared understanding/theory of the code, rather than for me to go off on my own for a while and then come back with a giant code dump. (This approach has never worked well for the project IMO).

alexcrichton commented on PR #15051:

Personally the lifting/lowering paths are what I'm extremely worried about. That's already full of tons of subtle code which requires a broad agreement amongst a bunch of points in the system, and getting it wrong on lifting/lowering is typically a CVE. I'm also personally quite worried about the piecemeal implementation with an incomplete spec as it increases the likelihood that by the end of things we have inconsistent implementations (accidentally) internally which reflect older versions of the specification or were just temporary artifacts that were forgotten to remove.

This approach has never worked well for the project IMO

I might feel a bit different on this -- I feel that the approach with the WASIp2 implementation and component-model-async implementation both worked quite well. The implementation was fully developed out-of-tree, yes, but the crucial part was that it landed piecemeal. This enabled being able to validate everything works end-to-end (the fork's CI), while still making everything reviewable (incremental landing in-tree). Personally I find it much easier to review incremental pieces with an end-state to refer to, and I also like to review high-level decisions on the end state before going too deep on the smaller decisions.

I understand the desire to empower toolchains to give feedback, but I'm hesitant of the strategy of "build everything in Wasmtime" and then ask for feedback. Rather I think it would be best for this to be more interactive with high-level feedback before an implementation and then in close coordination throughout the implementation. Without feedback during the implementation we risk spending a lot of time reviewing, auditing, etc, code that ultimately ends up all getting thrown away. To me this is sort of the poster child for development in a fork where we want to enable rapid experimentation with low overhead on review/implementation.

Which is all to say, I wasn't thinking of a fork when originally reviewing this, but now I'm feeling that a fork might be the best course of action. The fork would be similar to WASIp2 and component-model-async where development all happens externally and then is landed here in the main repo incrementally, so it's not just one giant code dump. The review would also probably originally be done at a high-level on the fork first before peeling things off here.

As a counterexample, proof-carrying-code was developed "in-tree" (with almost daily PRs!) but ended up not being quite the right shape once we got further along and discovered some issues; a decent amount of review overhead was spent there, and we ended up deleting it later.

I think other kinds of work are definitely suited to in-tree development, probably actually most work -- any kind of incremental improvement or migration. The above isn't meant to say we should have lots of long-running forks; only that they do have their place when the idea itself is speculative or subject to change, IMHO.

If yes, the build-the-thing-and-then-slough-off-layers-to-review both (i) saves reviewer time by whatever "rework factor" the initial path took, and (ii) as Alex says, gives a north star. "This little detail may not make sense here but I promise, it's essential in four steps". That sort of discussion is much harder to have speculatively and, I think, if we have a rule that an excursion should not go too far ahead of the review frontier, we may end up in local maxima -- one could never explore a speculative idea to see if it works.

The important thing to make it work I think is the attitude about rework/adjustment once the review phase does come; the existing proven-path-to-the-goal should be seen as speculative still, as the review frontier scans over it and adjusts design with more input. But having the working artifact is very, very valuable: even during review, one can rebase the rest-of-the-path on the existing thing to see if the review suggestions actually work in the end, or not (also avoiding later rework if a conflict is discovered!).

As a counterexample, proof-carrying-code was developed "in-tree" (with almost daily PRs!) but ended up not being quite the right shape once we got further along and discovered some issues; a decent amount of review overhead was spent there, and we ended up deleting it later.

I think other kinds of work are definitely suited to in-tree development, probably actually most work -- any kind of incremental improvement or migration. (Two examples from my end: exception support and initial guest debugging both had a pretty clear path and were built + landed in pieces.)The above isn't meant to say we should have lots of long-running forks or dev branches; only that they do have their place when the idea itself is speculative or subject to change, IMHO.

I only have weakly-held opinions about CM+GC and it seems plausible to me that it could go either way; just thought the above framework might be useful...
