I might recommend using a version field rather than a size field (or maybe both?) -- I've had some good experience with that in the past over in wit-bindgen. With just a size field then it might still be possible to read uninitialized padding bytes for example where trailing bools might not resize the structure due to padding but are otherwise uninitialized. With a version field where documentation can be added for "this field was added in this version" that might help with that problem.

IIRC I've seen other C libraries have a version field as well, such as with the curl library.

I think this might technically be unsound given MIRI-style rules because this is aserting that all of config is valid initialized memory for WasmBenchConfig which isn't the case for padding bytes an added fields. I think the only 100% safe way to model this would be to preserve the raw pointer under-the-hood and go to fields through raw pointers (not through &WasmBenchConfig).

Another possible example is if the latest version is version 2, but this is given version 1. In that case the accessor of cache below currently goes through &WasmBenchConfig but that pointer is actually invalid for version 1 because version 2 presumably added more fields so we'd be tricking rustc into thinking there's more fields than there actually are.

This is a pretty minor concern though and may not actually end up causing any issues in practice.
