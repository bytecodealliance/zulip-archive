vamsi3 opened PR #14717 from vamsi3:x64-overflow-flag-branches to bytecodealliance:main:

Closes #14716

Adds the x64 flag-branching rules for usub_overflow, sadd_overflow and ssub_overflow, matching what #14228 and #14254 did for uadd_overflow. A brif on the overflow result now jumps on the flags of the add/sub instead of going through setcc + test.

Each op gets the same two rules as uadd_overflow:

  • an is_nonzero rule in inst.isle using the add/sub flags (CC.B for usub_overflow, CC.O for the signed ops), with the value result as an opportunistic def;
  • a lower rule in lower.isle that emits only the add/sub when the overflow result has no other uses.

Up to 64 bits only, like uadd_overflow; i128 is unchanged. As with uadd_overflow, if the value is used before the branch, the branch is in another block, or the flags have several uses, the add/sub gets emitted again for the branch. This relies on #14324 so a sunk load isn't duplicated. aarch64 can follow separately.

Example (usub_overflow at i32, value used in the taken block), 42 -> 35 bytes:

 subl    %esi, %r8d
-setb    %r9b
-testb   %r9b, %r9b
-jne     0x21
+jb      0x1a

Tests:

  • isa/x64/sadd_ssub_usub_overflow_brif.clif: precise-output, modeled on uadd_overflow_brif.clif. Covers each op at i8 and i64, the value used/unused, the value used before the branch, the flags with several uses, the branch in another block, a load that must not be sunk (#14272, #14324), and trapz.
  • runtests/sadd_ssub_usub_overflow_brif.clif: interpret + run on x86_64, modeled on mul_overflow_flag_consumers.clif: each op at all four widths around the overflow edges, checking both the branch and the value, plus the flags both branched on and returned.

No existing expectations changed.

I measured this in a compiler of mine where every integer add/sub is overflow-checked, on Cranelift 0.136 with the is_nonzero rules backported. Instruction counts over its 11 benchmarks went down 2.3% overall (fasta -12.4%, the rest 0 to -5%).
