Add a public extensions field to the p3 Request and Response types.

This allows embedders to attach host-side data to a request or response and to retrieve it through the Resource. For example, this allows the host to stash information associated with the request or response without placing it in headers. This change does not allow the guest to observe or construct extensions. Requests and responses created by the guest start with an empty set of extensions.

My specific use case is that I need to associate metadata with a request that came in with a header, but I want to strip this header from the request before forwarding it to the guest. The guest is able to use host calls to interact with this metadata, but should not be able to observe the value directly. By putting this in the extensions, I can reach the metadata through the Resource handle rather than having to rely on something like the address of a reachable Arc that should be unique to the Request.

I had considered and rejected several alternatives:

  • Keying off of Resource::rep() - if the guest drops the request and creates a new one, it may reuse the u32 id
  • Tracking with TaskGroupHook - tracking guest->host and host->guest calls cannot handle the case where a request or response migrates to a different task
  • WorkerState::RequestData - does not work with custom worlds using wasi:http types, and is only available via WorkerState::on_request_start
  • forbidden_header_filter() and re-parse the header on host calls - forbidden headers are stripped before entering the guest via FieldMap::new_immutable; additionally, this is expensive for my use case

There is a behavior change: extensions that were previously dropped when converting between http and p3 types now pass through the guest. A concrete example is that hyper's client records non-canonical HTTP/1 reason phrases as an extension. If the guest returns this response and the host forwards it through to a hyper HTTP/1 server, that server will now write that non-canonical phrase to its client.

New tests verify that extensions survive a guest forwarding a request or response unchanged, and that the reason phrase from the hyper client survives as a hyper::ext::ReasonPhrase extension.

One gap: ProxyHandler drops extensions, so users of ProxyHandler will still not be able to access extensions associated with the request. This is one-sided: the response extensions are not stripped, so a response given to a guest and returned from the guest will preserve extensions. I am happy to open up a follow-up PR to address this gap.
