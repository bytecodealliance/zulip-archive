Victor Adossi (Oct 22 2026 at 05:22):

The reason I think it's hard to generalize here (at least I thought -- really would be happy to be corrected here) is that the way these engines all work is slightly different:

Perry goes to LLVM IR
Porffor goes to C
QuickJS is a embeddable engine in C (usable from rust in the case of componentize-qjs)
Boa is an embeddable engine in Rust

The embeddable engines in X (that can be used from Rust) basically all fit the wit-dylib shape

Porfor/Perry seem a little less like the same shape, only because even after you generate bindings you need to plug into their linking mechanism to get the shims you want natively. Wrapping the binary in a generated Wasm/Rust shell is also a great fast option but is just slightly less efficient (perfectly OK IMO) -- "old" componentize-js splicing embedder does just that (built for the engine use case, of course) w/ C++, "new" componentize-js dynamically generates the WASM (!) for the connection points.

So there are like... a few points in the space, I think we might even be able to name all of them:

  1. Fully native, your language toolchain chain reads WIT and puts the right exports and imports on the binary directly
  2. Partially native + custom linked, your language toolchain produces some of the right exports/imports, and you generate some extra code that links directly to the first batch of code
  3. Partially native + wrapped, your language toolchain produces some of the right exports/imports and you wrap the entire output and always jump from wrapper language A to your actual language B.
