Mendy Berger (Oct 23 2026 at 04:27):

still has a runtime that needs to be adapted per-library

Not sure exactly what you mean. There's no custom wasm runtime. There is however some glue code that each engine/compiler needs, ~400 lines per engine in the examples. But that glue only moves numbers and bytes between core wasm and JS: calling exports, calling imports, reading/writing memory, UTF-8. It doesn't depend on the WIT world at all.

The benefit is everything that does depend on it: lifting and lowering records, variants, lists, strings, resources etc. to and from JS values, and checking the exports. That's generated once, in JS, so it runs on any engine. Without it, each engine needs its own componentize tool that reimplements all of that natively, the way ComponentizeJS does for SpiderMonkey.

FWIW I think the glue can be reduced further, I started with what Jco and ComponentizeJS already had. But there will always have to be some amount of custom, per-engine code.
